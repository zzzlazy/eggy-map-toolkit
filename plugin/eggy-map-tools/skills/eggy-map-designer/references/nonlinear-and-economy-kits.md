# 生存、争夺与经营基础件套件

本文件为生存、积分争夺和经营地图提供可展开的结构蓝图。当前生存已有一个极简负面基线与一个高视觉/高逻辑复杂度对照，但都缺完整多人和连续回合实测；积分擂台缺少 3V3 实测，生存经营与纯店铺经营也未完成整轮生产/存档实测。因此数量、多人公平、经济、并发与重置仍是待验证假设。本文件不绑定组件 EID，也不把示例数量当成配额；使用时必须标注证据状态，并把结论留给当前版本的灰盒和试玩验证。

## 当前案例校准

- [《case-018》](exemplars/case-018.md) 用 12 个运行时单位形成 60 秒掉落板生存的最小闭环，也暴露开局失足、安全观察不足和成品场域缺层；它校准的是原型下限，不是成品数量。
- [《case-022》](exemplars/case-022.md) 用 30 种模型展开 1,863 个运行时单位，并记录 4,031 个 ECA 触发；两种高频基础模型占约 90.9%，代码另有多模式、三类随机场地、四类天气、生命/观战/复活与下一轮。它支持“窄资产、高组织度场域 + 独立回合控制器”，但首屏奖励弹窗遮挡规则，且未跑完一轮。
- [《case-009》](exemplars/case-009.md) 用 13 种模型展开 1,049 个运行时单位，其中三类高频基础件约占 94.8%，并有 990 个 ECA 触发记录；它支持少资产词汇、高实例展开和选装/计分/返场分层，但不证明 3V3 公平、反雪球或完整重置。
- [《case-011》](exemplars/case-011.md) 直接显示生命/饱食/口渴/天数、背包、制作配方、工作台解锁和存档入口；代码还给出生产站、建筑上限、拆除折损、岛屿扩张与数十类建筑存档线索。它支持依赖图、可见压力和持久化所有权合同，但没有完成一次生产、升级或重进，经济数值和并发仍属暂定。
- [《case-014》](exemplars/case-014.md) 的首屏直接显示产品/机器/餐桌目录和 `0/25` 解锁进度，代码给出订货、入库、制作、烘烤、上柜、顾客、结账、员工和门口终点词汇；3,352 个单位中有 847 个可变形方块、178 个组件组、116 个悬浮文字、25 个按钮和 23 个座位核心。它支持纯店铺的双层经营状态与千件展开口径，但没有实际走完首次生产、升级或读档。

## 共用分层与账本

先把对象按职责分开，避免用机关数量冒充场景完成度，也避免让数千个装饰件各自参与物理：

- `COL`：少量连续碰撞代理，决定真实通行、阻挡和边界；
- `MASS`：大轮廓、地形、建筑壳体和场地包裹；
- `MID`：梁柱、平台、掩体、管线、货架、看台等中层结构；
- `ROUTE`：路线边、落点、侧翼口、得分口和运输方向；
- `MECH`：真实危险、资源台、加工站和可操作对象；
- `STATE_FX`：同源显示准备、危险、归属、容量、完成和故障；
- `LOGIC`：计时、生成、归属、计分、淘汰、交易、阶段和重置，单独计数。

所有重复族先声明局部 `U/V/F` 基向量、入口/出口、净空、碰撞代理、A/B/C 变体和共享件所有者，再交给参数化展开工具生成唯一世界实例。视觉变体不得暗改碰撞、路程、资源价值或操作窗口。

## 一、生存竞技场套件

### 基本扇区 `SURVIVAL_SECTOR`

参数：可玩半径 `Rplay`、安全核心半径 `Rcore`、扇区夹角 `Wedge`、扇区数 `N`。相邻扇区共享边界，所有出生点到首个安全选择的真实移动时间应等价。

| 子结构 | 单扇区展开种子 | 职责 |
|---|---:|---|
| 地面碰撞代理 | 1–3 | 连续可玩面、可坠落缺口与边界 |
| 地面表皮 | 6–18 | 扇形分缝、材质节奏和状态换肤 |
| 边缘包边 | 4–12 | 读出危险边界，不制造隐形凸点 |
| 选择结构 | 4–10 | 掩体、坡面、小平台或穿越口 |
| 危险插槽 | 2–5 | 只放标准化底座，真实机关另计 |
| 方向框与状态灯 | 4–12 | 定向、预告波次和安全/危险切换 |
| 外壳与看台接口 | 6–18 | 把场地包进世界，默认无碰撞 |

单扇区约 27–78 个空间实例。复制前先锁定接口和公平参数，再对地面表皮、外壳和非碰撞中层做不超过约 30% 的受控变化。

### 全场装配族

- `CORE_TELEGRAPH`：中心安全核、倒计时环、波次色带和终局框景；让玩家在动作前读到“哪里将安全/危险”。
- `OUTER_SHELL_SPAN`：看台、围墙、天空轮廓、远景机械或自然体量；只服务包裹、比例和镜头，不改变竞技场公平。
- `HAZARD_FAMILY`：危险本体、扫掠范围提示、启动预告、冷却外观和清理接口；每类危险必须能单独教学和归因。
- `SPECTATOR_RING`：淘汰后的安全观战位、视线框、返回/结算提示；不得让观战对象继续碰撞或触发比赛。
- `ROUND_GATE`：出生保护、统一开局、终局锁、平局处理和下一局清空的空间载体。

六扇区成品示例可这样估算：扇区 `6×52=312`，中心与波次预告约 70，外圈壳体与看台约 260，危险底座及状态件约 110，出生/观战/结算约 80，远景与收缝约 52，总计约 **884 个空间实例**；计时、淘汰、波次和清理逻辑另计。该数字只展示如何从装配族得到数百件，不代表最低标准。

### 公平与阶段锁

- 先比较出生到安全核、两个相邻掩体、首危险插槽和脱离口的实测时间，再谈外观对称。
- 阶段升级一次只改变速度、密度、组合或可玩面积中的一到两个变量；任何组合都要保留至少一条可读解。
- 危险切换必须遵守“预告 → 生效 → 结束 → 清理”，新阶段不得与旧阶段残留意外叠加。
- 终局锁后停止生成、移动、淘汰和计分；无人存活、同时淘汰和平局都要有明确路径。

### 回合控制与入口层

- `ROUND` 是唯一总闸门；模式、场地事件、天气、玩家生命和可选能力都只能在 `ROUND=LIVE` 的授权下运行，不能各自开始/结束一局。
- 模式提交后冻结本轮生命、得分线、候选事件池与难度；中途改模式只进入下一轮待生效值，避免活动机关读取到一半新一半旧的配置。
- 场地事件和天气各自使用代次与 `SELECT/TELEGRAPH/ACTIVE/CLEANUP`；兼容矩阵逐格声明允许组合、保留解、最坏出生点与清理责任。
- 可选教程、礼包、商店或能力面板不得自动遮住出生观察面，也不得成为开始计时、取得控制或离开安全区的隐含前置条件。
- 无输入基线至少观察到一个设计终端：不会提前胜利、不会在读完首个提示前不可避免淘汰、不会无限等待房主/弹窗；需要玩家主动开始的派对房则提供明确可退出的等待态。

## 二、积分争夺场套件

### 核心装配族

| 装配族 | 展开种子 | 关键接口 |
|---|---:|---|
| `TEAM_SPAWN_WEDGE` 队伍出生扇区 | 45–85 | 保护区、两条离场边、首资源视线和回防口 |
| `RESOURCE_NODE` 资源节点 | 18–42 | 生成面、拾取/占领面、归属显示和枯竭/刷新显示 |
| `HOTSPOT_PLAZA` 高价值热点 | 70–140 | 至少三条进出边、中心冲突面、侧翼和撤离视线 |
| `SCORE_GATE` 交付/得分口 | 24–55 | 入口漏斗、判定面、成功反馈、重复计分防护和逃离边 |
| `NEUTRAL_LANDMARK` 中性地标 | 25–70 | 全场定向、热点迁移提示和不会偏袒一侧的遮挡轮廓 |

场地先以行进时间图建模：每个出生到低风险资源、高价值热点、最近得分口和主要侧翼都要有同等级成本。几何可不完全镜像，但关键路程、净宽、视线暴露、掩体收益和资源刷新必须可比。

四扇区首版示例：出生扇区 `4×62=248`，六个资源节点 `6×28=168`，中心热点 118，四个得分口 `4×36=144`，侧翼桥/坡/掩体 126，中性地标与外壳 86，总计约 **890 个空间实例**；比分、携带物、归属、掉落、刷新、追赶和结算逻辑另计。

### 反雪球检查

- 领先是否同时获得更多资源、更近交付和更强位置；若三者叠加，至少拆掉一层优势。
- 落后方的追赶窗口必须改变一个决策，而不是直接赠送不可反制的分数。
- 高价值热点要有暴露和撤离成本；低风险资源保证落后者仍可行动，但效率不能完全替代冲突。
- 携带、掉落、交付和重复进入得分口都需幂等；比分达到上限或时间结束后立即进入唯一终局锁。
- 测试不能只看最终比分，还要记录资源控制率、首分时间、最大连续领先、翻盘发生点和出生压制时长。

## 三、经营与建造套件

### 生产单元 `PRODUCTION_CELL`

参数：宽 `W`、高 `H`、深 `D`、可见容量档位 `C`。接口固定为前侧玩家操作面、左/上游输入口、右/下游输出口、背侧维护/状态面和至少一个升级连接点。

| 子结构 | 单元展开种子 | 职责 |
|---|---:|---|
| 壳体、立柱与基座 | 12–28 | 形成可读机器轮廓和结构厚度 |
| 输入容器与入口管线 | 8–20 | 显示原料来源、类型和容量 |
| 加工核心与运动外观 | 10–26 | 表达加工而非承担全部逻辑 |
| 缓冲仓 | 6–16 | 显示等待、堵塞和满载 |
| 输出容器与交付接口 | 8–20 | 对接下一站或玩家领取 |
| 运输、法兰与支架 | 10–30 | 连续连接，端点不能悬空消失 |
| 状态灯、刻度与故障件 | 6–18 | 同源显示待机、加工、完成、满载和故障 |
| 升级外观 | 8–24 | 只在升级后启用，表现真实能力变化 |
| 连续碰撞代理 | 1–4 | 保持高频操作面净空 |

单元约 69–186 个空间实例。A 初级、B 升级、C 满载/故障变体必须共享操作面、输入输出位置和安全净空；变体通过可见容量、额外管线、并行加工位或更清晰状态改变玩家决策，不能只换颜色。

### 世界装配族

- `INPUT_YARD`：原料来源、领取台、初次教学、容量演示和回收口；玩家首次进入应在一个短循环内看到完整交易。
- `CELL_ROW`：若干生产单元、共享管廊、玩家通道、维护侧和扩建接口；共享梁柱与碰撞代理需在总账扣除。
- `DELIVERY_BAY`：运输终点、交付台、收益反馈、退货/失败口和下一目标预告。
- `STORAGE_AND_WIP`：订货箱、储藏库存、原料容器、在制品槽与溢出回收；每次搬运都有来源、目的地、容量和失败归还。
- `RETAIL_COUNTER`：上架槽、产品/价格/库存、顾客读取面、结账结果和重复出售锁；商品模型只显示状态，不充当库存真值。
- `DEMAND_AND_SEATING`：顾客入口、选购/排队、座位、用餐、待结账和离店路径；无货、无座、等待超时与终局都能释放占用。
- `STAFF_STATION`：员工招募、任务认领、工作路径、交接和空闲返回；自动化不得与玩家手动事务同时消费同一批货。
- `UPGRADE_GALLERY`：可比较的升级卡位、所需资源、能力变化预览、购买结果和重复购买锁。
- `FACTORY_SHELL`：厂房外墙、屋架、吊具、远景设备、装卸口和照明节奏；默认与真实生产逻辑解耦。

四单元小型工厂示例：四个生产单元 `4×128=512`，输入场 118，交付湾 105，升级廊 96，共享运输/管廊 170，厂房壳体与屋架 190，路标、状态总览和收缝 63，总计约 **1,254 个空间实例**；资源、容量、加工队列、交易、升级、阶段和持久化逻辑另计。

店铺型地图把运输线改成“储藏—制作—烤制—上柜—桌位/结账”的人行货物流。首版可由：店铺壳体/街景 650、六个站点组件组 `6×145=870`、储藏与陈列 360、柜台/结账 180、桌位与顾客路径 420、员工/升级/总进度 210、灯光导视和主题收缝 260，合计约 **2,950 个空间实例**；碰撞代理、货物状态、顾客/员工和事件逻辑另计。该示例只校准“如何组织上千件”，不是复制案例数量或要求每张经营图达到三千件。

### 可见经济与重置

- 每次交易写成 `输入与归属 → 容量校验 → 原子扣除 → 加工/运输 → 原子产出 → 同源反馈`，失败不能停在扣了输入却无产出的半状态。
- 每件货物或批次贯穿 `ORDERED/STORED/WIP/READY/HELD/STOCKED/SOLD` 中适用的状态，始终有唯一位置和所有者；模型显隐、库存文字与收益都从这条记录派生。
- 容量必须在空间中可见：容器档位、堆叠、灯带或机械开合至少选一种；简介数字不能成为唯一信息源。
- 升级要改变容量、速度、路线、并行度或新功能中的至少一项，并让玩家在下一个循环中感知差异。
- 员工与顾客分别使用“认领—工作—交付—释放”和“到达—选择/落座—消费—结账—离开”生命周期；目标被删、等待超时、玩家掉线、终局与加载时都要关闭孤儿任务。
- 长期进度记录稳定的必需解锁集合，UI 计数从集合复算。达成后先锁完成快照、关闭未提交事务，再启用唯一出口/结算；加载时先重建世界与目录，再决定出口状态。
- 多人同时操作时指定资源所有者、站点占用和冲突策略；断线、死亡、重进和阶段结束都要处理队列中的对象。
- 若当前能力无法可靠持久化，把经济限定为单局闭环；新局清空资源、生成物、队列、购买锁和展示状态。

### 存档所有权与世界重建

- 先列快照范围：资源与容量、建筑类型/位置/朝向、生产队列、升级、区域解锁、阶段目标和一次性奖励；临时生成物、飞行道具、提示和本局锁明确排除。
- 店铺型快照还要说明产品/机器/桌位解锁集合、柜台库存、顾客/员工是否保存、终点解锁和未结算订单；通常重建顾客与临时任务比直接保存半个行为树更安全。
- 明确权威粒度：每名玩家、每个队伍、每块经营区或房主世界只能选一种。若能力限制为房主/一号位保存，要在进入前显示，并定义其他玩家的投入、退出和回滚。
- 保存前冻结或排空正在提交的交易/放置，写入完成后再反馈成功；加载时先清理默认/旧实例，再按稳定 ID 恢复一次，最后恢复队列与交互。
- 版本升级要有缺字段默认值、已废弃建筑迁移和超界对象回收；读档失败进入安全的新局或保留旧快照，不生成半个世界。
- “继续”与“新局”是两条权威分支。新局清除资源、建筑、队列、升级、解锁、排行榜临时值和生成物；第二次进入不得重复领取一次性奖励。

## 共享展开账格式

大型方案至少维护下表；每个区域或状态一行，公式与实际展开结果必须对账。

| 区域/状态 | 装配族 | 重复数 | 单体展开 | 空间实例 | 碰撞代理 | 状态显示件 | 逻辑对象 | 峰值可见 | 峰值活动逻辑 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 示例 | `SURVIVAL_SECTOR` | 6 | 52 | 312 | 12 | 48 | 0 | 210 | 0 |

交付前回答：

1. 每一批重复件是在形成轮廓、接触面、路线语义、状态反馈还是主题纹理；纯凑数是否已移除？
2. `COL` 是否足够少且连续，视觉微件是否默认关闭物理和不必要投影？
3. 峰值镜头真正看见多少对象，峰值时同时活动多少危险、资源、队列、计时器和生成物？
4. A/B/C 变体是否保持接口与公平，只改变经声明的表皮或能力？
5. 降级顺序是否先减远景、微表皮、投影、透明与非关键动画，保留路线、危险、交互和目标反馈？

将空间实例结果送入密度审计，将资源/淘汰/计分/交易转换送入状态审计，并把两者峰值写回完整设计总账。只有这样，“上千件”才代表被组织的场所，而不是撒满地图的装饰。
