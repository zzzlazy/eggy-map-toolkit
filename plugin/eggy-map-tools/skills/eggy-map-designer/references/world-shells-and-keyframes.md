# 场所形态、世界壳体与关键镜头

本文件回答“玩法拓扑已经成立后，玩家实际身处怎样的场所”。它位于灰盒与逐件坐标之间：把抽象节点组织成有包裹、尺度、景深、状态和转场的视觉场景，再把场景交给装配族展开。若只写一块大地板、若干机关和一圈装饰，玩法可能能跑，但世界壳体仍未成立。

组件名称、EID、碰撞尺寸和坐标轴必须以当前版本证据为准。本文件中的形态、视角和数量关系都是设计合同，不是游戏常数，也不是从某张公开地图复制的配方。当前案例只部分支持峡谷廊道、室内房间、赛道、垂直长线、展示景观和混合尺度等局部方法；证据强弱与题材边界以 [视觉主题与世界构成蓝图](visual-theme-playbooks.md) 为准。

## 五个对象不要混用

| 对象 | 回答的问题 | 常见误用 |
|---|---|---|
| 玩法拓扑 | 玩家能从哪个状态到哪个状态 | 把一条箭头当成场景 |
| 世界壳体 | 路线周围哪些体量、边界与远景让它成为场所 | 把天空盒或一块地板当成壳体 |
| 视觉场景 | 哪一段在同一比例、主轮廓与光材规则下被阅读 | 按机关数量切段，导致每段只有一个装置 |
| 装配族 | 哪些基本件以稳定接口组成墙跨、岩壁、平台、看台或家具 | 用一个 Prefab 名称代替展开 |
| 关键镜头 | 玩家在真实相机位置必须同时读到什么 | 只验收俯视编辑器截图或详情封面 |

一个玩法节点可以与相邻节点共享同一壳体；一个大型节点也可以包含多个视觉场景。切分依据是比例、轮廓、包裹、主要装配族或世界状态是否发生明显变化，不是为了多写章节名。

## 先选场所形态

形态独立于题材。同一工业主题可以做成廊道、竞技场或开放厂区；同一峡谷主题也可以承载竞速、探索或生存。先按玩家关系与相机选择主形态，最多再用一个门槛形态完成转场。

| 形态 | 常见拓扑/主类型 | 壳体最低关系 | 密度真正应投向 | 主要风险 |
|---|---|---|---|---|
| `linear_corridor` 线性廊道/峡缝 | 竞速、章节、潜行、叙事 | 连续接触面、至少一侧主质量、周期性顶框/门槛、远期目标 | 转折、落点侧脸、支撑、洞口和恢复口袋 | 直线平铺、全程同宽、终点从出生就暴露 |
| `room_sequence` 房间—走廊序列 | 解谜、叙事、经营、潜行、恐怖 | 房间功能壳、门窗/服务口、走廊接口、回望标记 | 门槛、功能家具簇、机电、操作面和房间状态变体 | 空盒复制、家具填满、所有门相同 |
| `arena_bowl` 竞技场/体育场 | 生存、积分、Boss、回合、体育 | 公平接触面、外边界、中心/侧翼参照、看台或远景框 | 场区边线、扇区接口、危险/资源底座、观战与结算焦点 | 装饰改变公平、视线遮挡预告、场外没有尺度 |
| `hub_spoke` 地标中心—辐射节点 | 探索、社交、防守、解谜 | 可反复看见的中心地标、各支路门槛、返回视线 | 中心轮廓、支路身份、回流门、完成状态和导航层 | 每条支路同貌、中心过密、回程只靠文字 |
| `open_district` 开放街区/网络场 | 经营、争夺、沙盒、阵营推理、探索 | 可读分区、至少两个交叉参照、边界与返回网络 | 分区立面、热点、侧路、可见生产/任务状态 | 空旷大板、远景不可达、玩家失去共同方位 |
| `loop_track` 环线/车辆赛道 | 载具竞速、计圈、巡游 | 连续路面、内外边界、弯前视距、维修/复位口 | 道路侧脸、护栏、弯道标志、跨越点和看台节奏 | 用步行尺度、弯后盲墙、复制直路凑长度 |
| `vertical_stack` 垂直塔/深井 | 章节、攀爬、生存、垂直探索 | 每层落点、上方目标、侧向参照、下方回收、层间框 | 层缘厚度、支撑、相机口袋、检查点与远近层叠 | 上层底面遮挡、长坠落等待、跨层越序 |
| `branch_rejoin` 双线分流—会合 | 合作、竞速、潜行、选择叙事 | 分流前共同预览、各线身份、跨线因果、会合容量 | 分流门、角色/风险语义、对侧可见反馈和重聚地标 | 两条独立跑道、装饰按钮、一路永久更优 |
| `multi_scene_threshold` 多场景/尺度门槛 | 长章节、叙事、巨物微缩、传送换景 | 离场快照、建立镜头、尺度锚点、入口/出口、清理所有者 | 门槛前后轮廓差、熟悉物比例、加载遮挡与返回锚点 | 突然换素材包、控制恢复后无方向、旧场景残留 |
| `showcase_panorama` 展示全景/活动岛 | 社交、演出、沙盒展示 | 角色清楚的前景、可达活动中景、主地标远景、返回中心 | 合影框、活动台、站位净空、灯光焦点与换景出口 | 只有背景、活动不可达、粒子吞掉人物 |

## 世界壳体卡

每个视觉场景建立一张 `world_shells[]` 卡，并写入设计总账 `theme`。字段不是美术文案；它们把拓扑、节拍、装配和真实相机绑在一起。

```json
{
  "name": "ENTRY_CANYON",
  "topology_nodes": ["START", "TEACH"],
  "beats": ["orient", "flow"],
  "assembly_zones": ["ENTRY", "FIRST_RUN"],
  "silhouette": "两侧倾斜岩壁夹出远处断桥门形",
  "enclosure_strategy": "连续地面与左侧主岩壁承担实体包裹，右侧断崖和顶框控制开合，远山只作尺度",
  "depth_layers": {
    "foreground": "出生接触面、低矮挡边与最近路线缝",
    "midground": "第一个可达平台、门框与安全展示机关",
    "background": "断桥剪影和终章山口，均不伪装成当前落点"
  },
  "scale_anchors": ["玩家可穿过的旧工程门", "重复出现的护栏与铆钉间距"],
  "assembly_families": ["岩壁段", "栈道支座", "工程门架"],
  "state_variants": ["进入时完整且安静", "教学提交后远处桥灯亮起"],
  "transition_in": "出生相机在安全口袋内取得控制",
  "transition_out": "转折门框先遮住旧路线，再展开下一峡段",
  "review_views": [
    {
      "name": "SPAWN_FIRST_SCREEN",
      "kind": "spawn",
      "camera_intent": "不移动镜头即可理解场所、第一动作和远期方向",
      "must_show": ["主剪影", "最近路线", "一个尺度锚点"]
    },
    {
      "name": "FIRST_ACTION",
      "kind": "action",
      "camera_intent": "在真实助跑相机中同时看见落点、危险边和出口框",
      "must_show": ["起跳面", "完整落点", "失败恢复方向"]
    }
  ]
}
```

### 卡片硬约束

- `topology_nodes` 与 `beats` 只能引用总账中存在的名称；最终方案覆盖全部节点和节拍。节拍只归一个壳体，门槛节点可以被前后壳体共享。
- `assembly_zones` 至少一个，并使用参数化装配/密度账中的真实区域名。准备部署时，所有可见区域都必须归入至少一个壳体，壳体声明的区域也必须确实有展开实例；这样不能只在文案里写多场景、却把组件堆到一个区。
- `silhouette` 说明可画出的质量关系，不能只写主题名或颜色。
- `enclosure_strategy` 明确哪些面是实体、哪些开放、哪些只是远景；开放场也必须有地面边界、水平参照或远景框中的至少两项。
- `depth_layers` 分别写前景接触/角色框、中景可达动作和远景方向/尺度；三层不能都是装饰名词。
- `scale_anchors` 至少两个，并能从玩家相机复述比例；栏杆、门、座椅、包装边、窗层、车辆或角色雕像都可承担，但要与玩法尺度一致。
- `assembly_families` 至少两个，且必须来自主题卡的全局装配族；这阻止场景脱离共享形状语法。进入最终装配时把描述名冻结为参数化计划中的精确族名；每个族都要在本壳体的 `assembly_zones` 中产生可见世界实例，不能只在总账里挂名。
- `state_variants` 至少包含基线与一个真实状态结果。只改颜色但不改变玩家信息或情绪，不算第二状态。
- `review_views` 每个至少列出三个必须同时可见的信息。取得控制后的相机是权威画面；编辑器俯视图、详情封面和过场镜头只能作补充。

按密度档设置最少场景数：`micro_space/themed_short` 可以只有一个完整壳体，`multi_scene` 至少两个，`long_world` 至少三个。数量只是防止把多场景总量堆在一个首屏；若同一连续世界需要更多壳体，应按比例、轮廓、装配族或状态转折继续拆分。

## 关键镜头账

`review_views[].kind` 使用下列有限集合，使不同地图可以用同一套验收：

- `spawn`：取得控制后的第一屏；覆盖入口节点的壳体必须有一项；
- `entry`：穿过门槛后重新建立方向；
- `action`：真实操作相机中的起点、目标、风险和退出；
- `reveal`：新轮廓、规则或状态被看见的奖励镜头；
- `recovery`：失败后恢复控制，能立即判断自己在哪里；
- `return`：回到旧场景时能比较状态变化；没有回访的地图不强求；
- `terminal`：终局、结算或主动退出；覆盖终端节点的壳体必须有一项。

每个壳体至少有两个关键镜头；通常从进入、核心动作和离开中各取一个。镜头不是摄影清单，而是组件分配依据：某一件若不服务任何关键镜头、接触面、状态或性能代理，就不应仅为填空被复制。

### 每屏三层信息

| 距离 | 必须回答 | 可以省略 |
|---|---|---|
| 前景 | 玩家站在哪里、接触边多厚、角色是否被遮挡 | 不影响轮廓的微装饰、不可见背面 |
| 中景 | 下一步能到哪里、危险来自哪里、交互结果在哪 | 与当前决策无关的远支路细节 |
| 远景 | 长期向哪里、世界多大、当前章节属于哪里 | 逐件碰撞、完整内饰和高频动态 |

若一屏只剩前景，玩家会失去方向；只有远景则像不可达布景；三层都高饱和、运动或发光时，重点仍等于没有重点。

## 从壳体卡分配基本件

不要先给全图定一个平均件数。依次为每个壳体分账：

1. **宏观质量 `MASS`**：接触地形、侧向包裹、顶框、远景主质量和主剪影；先用少量大件闭合关系。
2. **中层结构 `MID`**：支撑、转角、洞口厚度、檐口、看台、管线、护栏、房间接口；这是把灰盒变成可信场所的主要增长层。
3. **路线与接触 `ROUTE/CONTACT`**：落点、边线、场区、操作面和恢复口；与真实碰撞代理分开记。
4. **功能道具与状态 `PROP/STATE_FEEDBACK`**：只在动作、回访、尺度或主题叙事需要处增加。
5. **氛围 `FX`**：服务景深、状态与焦点；不承担本应由体量和结构完成的包裹。

再把每个装配族沿壳体的局部基向量展开。重复件的意义来自位置、轮廓、接口或状态变化；把平面机械切碎、在不可见背面铺细件、把逻辑对象计作景观，都不能补足壳体。

### 形态对应的降级顺序

| 形态 | 优先保留 | 性能不足先减 |
|---|---|---|
| 廊道/垂直 | 接触面、侧向轮廓、转折框、下一目标 | 不可见背面、远景岩片、重复小附着 |
| 房间序列 | 门洞、功能家具、踢脚/顶网格、状态焦点 | 不可交互小家具、抽屉细件、远房投影 |
| 竞技场/体育 | 场界、危险/得分反馈、公平碰撞、预告视线 | 看台人物、远景旗帜、非焦点灯效 |
| 枢纽/开放网络 | 主地标、分区剪影、返回线、热点状态 | 不可达内饰、均匀地面散件、远区动态 |
| 赛道 | 连续路面、弯前视距、护栏与复位标记 | 远景车、路面微分缝、非近景看台 |
| 展示/演出 | 角色轮廓、站位净空、活动中景、主背景 | 非当前舞台粒子、密集小灯、不可达陈设 |

## 转场合同

相邻壳体之间至少改变高差、朝向、开合、比例、主轮廓或世界状态中的一项，同时保留两个连续线索，例如路线色、结构网格、主材质、地标方向或装配接口。转场逐项写：

- 离开前能否预见新场景，而不提前泄露全部答案；
- 何时遮住旧路线，何时建立新方向；
- 传送、过场、缩放或载具切换后，控制权在哪个安全相机口袋恢复；
- 失败或回访时使用哪一侧的状态快照；
- 多人跨场时，迟到者、掉队者和旧场景动态由谁清理。

只换天空、色板或 Prefab 包，不构成场景转场；如果比例和动作没有改变，应把它视为同一壳体的状态变体。

## 壳体验收

1. **覆盖审计**：所有拓扑节点和节拍都属于明确壳体；多场景/长世界没有把全部实例预算堆在出生区。
2. **首屏审计**：取得控制后，不转镜头即可看见主世界承诺、最近有效动作和至少一个尺度锚点。
3. **动作镜头审计**：在真实移动、载具、仰俯或多人相机中，起点、目标、风险与退出仍同屏可读。
4. **去资产审计**：隐藏少量主题 Prefab 后，`MASS/MID/ROUTE` 仍表达场所形态与主世界。
5. **回望审计**：有回访时，同机位能指出至少一个由权威状态造成的世界变化；无回访则验收终局画面。
6. **灰度与静音审计**：路线、危险、目标和节奏不能只靠色相或声音区分。
7. **边界审计**：视觉壳、真实碰撞、恢复区、相机口袋与不可达背景职责一致。
8. **峰值视区审计**：逐关键镜头统计可见、碰撞、投影、动态与透明峰值；按形态降级后仍保留轮廓、路线和反馈。

设计总账只能检查字段、引用与覆盖关系，不能判断文字描述是否真实。最终仍需用目标设备截图、实际操作与展开清单逐屏核对。
