# 专项主类型基础件套件

本文件把纯音游、Boss/PvE、防守、潜行、回合策略、体育、创造沙盒和阵营推理的系统接口展开成可参数化的基础件装配族。它不绑定 EID，也不证明当前版本存在某种伤害、寻路、谱面、私密分角或保存能力；先用组件目录与灰盒验证能力，再把“方块、柱、板、环、坡面、灯、状态面、连续碰撞代理”等角色映射为可写组件。

下面的件数是**组织示例**，用于防止方案退化成“地板＋机关＋装饰”。它们不是最低配额，也不是已测性能上限。每次使用都要按 [基础件装配与成品密度](assembly-and-density.md)、[参数化装配与坐标展开](parametric-layout.md) 和 [性能与降级预算](performance-and-budget.md) 展开、对账、测峰值并降级。

## 共用规则

每个装配族使用局部 `U/V/F`，声明 `W/H/D`、入口/出口、玩法净空、A/B/C 变体、共享件所有者和成本角色。先分开：

- `COL`：极少量连续地面、墙、边界和真实目标碰撞代理；
- `MASS`：舞台、建筑、山体、看台、竞技场或棋盘的宏观体量；
- `MID`：梁柱、分缝、框架、掩体、管线、座席、护栏和结构厚度；
- `ROUTE`：轨道、视线边、危险区、撤离线、球场线和合法格；
- `MECH`：实际可交互、攻击、传感器、比赛对象或编辑工具；
- `STATE_FX`：只从权威状态派生的判定、生命、波次、警戒、回合、比分和预算反馈；
- `LOGIC/SPAWNED`：控制器、计时、临时音符/投射物/单位/作品预览，另计上限与清理。

数千个基础件不等于数千个逻辑体。重复表皮默认无物理、少投影且静态；状态变化集中在少量可替换面、灯带或标记，碰撞由连续代理承担。

## 一、纯音游舞台

### 轨道跨 `RHYTHM_LANE_BAY`

参数：轨道宽 `W`、前读长度 `D`、提示高度 `Hcue`、轨道数 `L`。入口接上一跨的提示方向，出口对齐判定区；玩家/镜头净空覆盖整条来向。

| 子结构 | 单跨展开种子 | 职责 |
|---|---:|---|
| 连续地面/边界代理 | 1–3 | 保证表演区和不可达侧景稳定 |
| 轨道表皮与分隔 | 8–24 | 形成速度方向与轨道身份，不逐块参与逻辑 |
| 两侧骨架/舞台厚度 | 8–20 | 解释悬空舞台、遮住大底板 |
| 前读节拍框 | 6–18 | 固定来向与节拍尺度，状态由少量面切换 |
| 判定线/结果环接口 | 4–12 | 统一命中位置和反馈边界 |
| 灯带、线缆与收缝 | 8–24 | 只强化乐句与轨道，不制造必要信息单通道 |

单跨约 35–101 个空间实例；谱面音符和判定逻辑不计入静态装配。A 基础、B 交叉、C 长按/多层提示只改变提示槽与表皮，不能改变同一难度档的判定线和玩家净空。

### 世界装配族与展开示例

- `COUNT_IN_PORTAL`：取得控制、校准、静音/低闪模式入口和倒计时框；
- `RHYTHM_LANE_BAY × N`：沿直线、折线或环形展开，所有提示从同一方向进入；
- `PERFORMANCE_SHELL`：舞台侧墙、吊架、观众剪影、音响/机械远景，与谱面逻辑解耦；
- `COMBO_TOWER`：比分、连击与乐句进度的世界载体，不遮判定线；
- `RESULT_STAGE`：完成、重开、退出与下一首的清晰分支。

一个四乐句小舞台可由：八个轨道跨 `8×72=576`、倒计时/判定/结果 150、舞台壳体与吊架 260、远景观众与焦点 120、线缆灯带和收缝 94，共约 **1,200 个静态/状态空间实例**。音符密度、活动灯数和判定入口另列峰值，不能用 1,200 替代逻辑预算。

## 二、Boss 战斗场

### 战斗扇区 `BOSS_ARENA_SECTOR`

参数：可玩半径 `R`、扇区角 `A`、安全口宽 `S`。扇区接口必须无缝，攻击标记能跨扇区连续，表皮变化不得改变躲避路程。

| 子结构 | 单扇区展开种子 | 职责 |
|---|---:|---|
| 地面与边界代理 | 2–4 | 连续战斗面、Boss 边界和掉落恢复 |
| 地面表皮/攻击网格 | 8–24 | 让攻击来源、覆盖和安全边可读 |
| 掩体或高低选择 | 4–12 | 只服务已声明反制，不制造永久安全角 |
| 外环支撑与看台接口 | 10–28 | 包裹场地、建立尺度，默认静态无碰撞 |
| 安全口/复活口框 | 5–14 | 明确暂时恢复，不伪装成输出区 |
| 阶段状态边框 | 4–12 | 从 Boss 阶段权威派生 |

单扇区约 33–94 件。建议 6–10 个扇区环形展开；先锁定公平和攻击包络，再只改变外环、裂纹、旗帜、机械/自然附着。

### Boss 外观骨架 `BOSS_SHELL`

用 8–24 个大体块确定躯干/核心轮廓，20–60 个中件组成关节、装甲、角/翼和支撑，30–120 个小件处理面甲、纹理、发光缝与阶段破损。真实受击体、攻击源和移动代理单独建模；装饰肢体不能各自成为伤害入口。

八扇区示例：战斗扇区 `8×68=544`、Boss 外观 190、外环/看台 310、出生/复活/结果 120、攻击来源框与收缝 150，共约 **1,314 个空间实例**。投射物、预告面、弱点状态和攻击计时另列峰值。

## 三、防守 / 塔防场

### 路径跨 `DEFENSE_LANE_BAY`

参数：路径宽 `W`、跨长 `D`、插槽侧 `Side`。每跨固定入口、出口、敌人导航中心线、玩家跨越点和越界回收标记。

| 子结构 | 单跨展开种子 | 职责 |
|---|---:|---|
| 路面/阻挡代理 | 2–5 | 保持敌人与玩家的合法区域分离 |
| 路面表皮与方向 | 5–16 | 表达来向、波次与漏怪方向 |
| 侧墙/沟槽/桥架 | 8–24 | 防止路径漂浮，形成主题包裹 |
| 建设槽接口 | 0–2 个槽，每槽 8–20 | 显示占用、范围方向和升级连接 |
| 波次/受击状态件 | 4–12 | 只从路径与波次状态派生 |
| 收缝与远景接口 | 4–14 | 连接源点、弯角和核心 |

一跨约 23–91 件。转角、岔路和高差使用专门变体，不能仅旋转直跨后让寻路线穿墙。

### 关键装配族

- `SPAWN_SOURCE`：波次倒计时、敌人族预告、路线入口与生成回收；
- `DEFENSE_PAD`：底座、操作面、范围/职责提示、占用和升级外观；
- `LEAK_GATE`：一次漏怪提交、核心方向和重复触发保护的空间载体；
- `CORE_FORT`：核心碰撞、生命分层外观、修复/失败/结果框；
- `BUILD_PHASE_HUB`：资源总览、选择对比和启动波次，不堵主路径。

双路小场示例：十个路径跨 `10×55=550`、八个建设槽 `8×32=256`、两源点和漏怪口 120、核心要塞 150、壳体/远景/回路导视 260，共约 **1,336 个空间实例**。敌人、射弹和目标监听按同时存在上限另计。

## 四、潜行渗透场

### 潜行单元 `INFILTRATION_CELL`

参数：单元宽 `W`、深 `D`、视线主向 `F`。入口提供观察位，出口指向下一安全读图点；每单元只教或组合有限传感器规则。

| 子结构 | 单元展开种子 | 职责 |
|---|---:|---|
| 地面/墙碰撞代理 | 2–6 | 保证遮蔽与真实视线边界一致 |
| 建筑/地貌壳体 | 8–24 | 包裹路线并建立可解释的阴影区 |
| 遮蔽物与穿越口 | 6–18 | 提供观察、等待、绕行或工具落点 |
| 巡逻/视线框架 | 4–14 | 表达朝向、路径和危险边，不承担传感真值 |
| 状态灯/警戒传播 | 3–10 | 同源显示怀疑、警戒、搜索和恢复 |
| 屋架、管线、檐口与收缝 | 8–26 | 建立厚度和主题，保持镜头净空 |

单元约 31–98 件。A 观察、B 穿越、C 目标/撤离变体保持遮蔽判定和传感器接口，不允许视觉箱体看似遮挡却不阻断规则。

十二单元示例：潜行单元 `12×68=816`、任务/撤离地标 150、上下层或街区壳体 320、远景与回望构图 140、出生简报和警戒恢复 90，共约 **1,516 个空间实例**。传感器数量、同时搜索者和提示覆盖另计峰值。

## 五、回合棋盘 / 卡牌场

### 棋盘格 `BOARD_CELL`

参数：格宽 `C`、棋盘行列 `R×K`。每格拥有一个连续可选面、所有权边框、合法目标接口和最多一个占用锚点；相邻格分线由固定一侧计数。

| 子结构 | 单格展开种子 | 职责 |
|---|---:|---|
| 选择/占用代理 | 1 | 唯一合法格输入面 |
| 顶面与侧脸 | 2–6 | 建立格子厚度和棋盘轮廓 |
| 边/角标记 | 2–8 | 显示邻接、阵营或特殊规则 |
| 状态面 | 1–4 | 只显示合法、选中、占有或待解析中的一种来源状态 |

单格约 6–19 件。共享边必须扣除；合法性变化优先替换少量状态面，而不是让整格几十个件独立显隐。

### 世界装配族

- `BOARD_FRAME`：棋盘外框、坐标地标、旁观边界和终局焦点；
- `TURN_PODIUM`：当前玩家、剩余时间、确认/取消与非行动者等待；
- `ACTION_DOCK`：动作预览、成本、目标选择和提交反馈；
- `RESOURCE_RAIL`：公共/私有资源的世界位置，私有内容不朝公共镜头；
- `RESOLUTION_STAGE`：连锁来源、目标与顺序的短反馈区，不复制真状态。

六乘六棋盘示例：36 格 `36×12=432`、棋盘框 120、双方行动台与资源轨 `2×85=170`、解析/结果舞台 100、会场壳体与观众轮廓 180，共约 **1,002 个空间实例**。棋子、手牌、选择 UI 和回合逻辑另列上限。

## 六、体育比赛场

### 场地扇区 `SPORT_FIELD_SECTOR`

参数：半场长 `L`、宽 `W`、分区数 `N`。中心线、禁区/得分区、边线和重启点使用稳定形状语义；两侧变体只改变非玩法表皮。

| 子结构 | 单扇区展开种子 | 职责 |
|---|---:|---|
| 连续场地代理 | 1–3 | 稳定运动与出界边界 |
| 地面表皮/场线 | 5–16 | 区分方向、阵营、合法区与重启位 |
| 边缘厚度/护栏 | 6–18 | 防止大平面悬浮，不能形成意外反弹缝 |
| 侧翼坡/掩体/路线框 | 2–10 | 仅在玩法需要时提供选择 |
| 看台与广告接口 | 8–26 | 包裹比赛，不遮挡球门或远期视线 |
| 死球/比分状态接口 | 3–10 | 由比赛权威驱动 |

单扇区约 25–83 件。两半场应先通过行进时间、视线和反弹测试，再做受控外观差异。

### 关键装配族与示例

- `TEAM_SPAWN_TUNNEL`：阵营识别、出生保护、离场分流和回防视线；
- `GOAL_FRAME`：厚度、方向、合法判定面、得分反馈与防重复回收；
- `OOB_EDGE`：视觉边线、真实触发、最近重启标记和无球状态；
- `CENTER_RESTART`：开球倒计时、双方距离和第一合法触球；
- `STAND_BAY`：看台重复跨、远景观众、灯架和比分板支撑。

八扇区小场示例：场地 `8×58=464`、两球门 `2×62=124`、八个看台跨 `8×48=384`、出生/开球/重启 120、顶架/灯架/远景 150，共约 **1,242 个空间实例**。比赛对象、轨迹/持有反馈和接触逻辑不混入静态件数。

## 七、创造沙盒场

### 目录台 `CATALOG_POD`

参数：类别数 `C`、预览口宽 `W`。每台固定浏览面、预览位、成本/预算面、确认/取消和离开净空；目录模型只是选择表现，不等于已生成作品。

| 子结构 | 单台展开种子 | 职责 |
|---|---:|---|
| 台座/操作面/碰撞 | 3–8 | 稳定交互和多人站位 |
| 类别框与预览龛 | 6–18 | 让类别、当前选择和预览来源可见 |
| 成本/预算/权限状态 | 3–10 | 从权威预算和所有权派生 |
| 顶架、线缆、收缝 | 5–16 | 接入创作场壳体，不遮操作面 |

单台约 17–52 件。不同类别保留相同交互接口，只改变图形、预览载体与预算标签。

### 建造区 `BUILD_PLOT`

- 1–4 个连续地面/边界代理；
- 8–30 个边框、网格大分区和高度参照，微网格使用材质或少量状态面而不是逐格碰撞；
- 4–16 个出生、目录、保存、测试和退出导视；
- 8–30 个壳体/远景接口，为玩家作品保留中性背景与镜头空间；
- 预览、选择框、非法位置反馈均为有上限的临时对象，退出或测试时清空。

六目录台的基础创作场可由：目录台 `6×38=228`、两块建造区 `2×65=130`、保存/撤销/测试/展示台 160、工作室壳体与远景 300、导视/预算总览/收缝 110，共约 **928 个系统场景实例**。玩家作品另设例如 `0…B_player` 与 `0…B_world` 的独立预算；不能把未来玩家可能放置的最大值冒充初始完成度，也不能让场景壳体吃掉创作预算。

## 八、阵营推理场

### 任务 / 证据房间跨 `DEDUCTION_ROOM_BAY`

参数：房间宽 `W`、深 `D`、可见入口数 `E`、任务/事件接口数 `T`。每个房间先承担一个公共功能与一条可观察流线，再放任务或事件；不能为了制造怀疑刻意做无地标的同质走廊。

| 子结构 | 单房展开种子 | 职责 |
|---|---:|---|
| 连续地面、墙与门洞代理 | 2–6 | 保持真实路线、可见入口和封锁状态一致 |
| 房间壳体与功能大件 | 8–24 | 让房间从远处可按功能识别 |
| 通道框、门槛和观察边 | 6–18 | 提供时间/方向痕迹，不泄露角色身份 |
| 任务/证据站外壳 | 每站 8–24 | 显示占用、进展或事件结果；真状态另计 |
| 公共设备与状态件 | 4–14 | 从任务、破坏或修复状态派生，不显示操作者阵营 |
| 梁柱、管线、家具和收缝 | 8–26 | 建立可信场所、镜头尺度与局部遮挡 |

单房通常约 36–112 个空间实例。A 公共任务、B 交通节点、C 事件/修复变体保持门洞、任务台接口和公共色义；私密角色提示不能做成其他玩家可见的房间变体。

### 会议中心 `MEETING_HUB`

- 中央议事台与阶段边框 12–35 件，清楚区分场上、锁定、讨论、投票、解析与结束；
- 目标人数的独立投票位，每位 5–12 件，统一朝向公共结果但不让旁人读取未提交私票；
- 集合/传送落点、镜头净空与离场通道 8–24 件，会议开始和结束均不重叠卡位；
- 公共进度、存活名单与计时载体 6–20 件，只显示规则允许的汇总；
- 旁观/淘汰视角框与隔离边 6–18 件，不能靠位置或颜色泄露仍隐藏的信息。

### 关键装配族与展开示例

- `PRIVATE_BRIEF_CELL`：只向本人展示角色、合法动作与初始信息；共享镜头看不到内容；
- `INCIDENT_THRESHOLD`：报告/召集的空间入口、去重锁、场上动作冻结反馈和恢复标记；
- `VOTE_POD`：资格、选择、确认/修改、已提交与清理的界面外壳，真票由回合权威持有；
- `AFTERLIFE_ROUTE`：淘汰后的观战或有限任务路径，与场上碰撞、会议和私密信息隔离；
- `RESULT_REVEAL`：终局锁后再揭示允许的信息，并把再来一局入口与旧代清理分开。

十房小局示例：十个房间跨 `10×72=720`、会议中心 180、十二个分角/投票接口 180、通道与公共地标 240、旁观/结果/出生壳体 160，共约 **1,480 个空间实例**。角色 UI、选票、任务/事件状态、临时对象和交流系统另列峰值；不能以私密逻辑多为由减少场所辨识、路线痕迹和会议空间。

阵营推理首先受人数与信息边界约束。用单人机器人验证触发图只能证明流程可达，不能证明谎言、观察、讨论、公平或身份保密；任何公开房间颜色、专属出生口、共享特效或观战镜头都要做泄密审计。

## 跨套件展开与验收

每张地图先提交一张公式账：

`静态场景 = Σ(装配族单体件数 × 放置数) − 共享接口 + 独立地标`

`运行峰值 = 静态可见峰值 + 状态面峰值 + 动态机关/对象峰值 + 临时生成峰值`

然后回答：

1. 宏观体量、中层结构、接触/信息和表面/氛围四层分别有多少，低于预算是主动留白还是未完成？
2. 每个重复族是否有稳定接口和 A/B/C 序列，而不是逐件随机或整排完全相同？
