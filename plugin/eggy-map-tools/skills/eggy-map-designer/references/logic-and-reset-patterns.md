# 触发、状态机与重置模式

本文件定义设计层的逻辑合同，不虚构游戏脚本 API。实际实现前必须查询当前版本组件目录，逐条确认触发、条件、目标动作和可写属性；目录不支持的能力要改设计、降级或标记不可实现，不能把抽象状态名写进未知 `properties`。

现有案例缓存能证明检查点、事件、角色权限、任务对象和场景状态等系统存在，但通常不能还原完整触发图。以下模式主要是可靠性蓝图，不得冒充某张案例的精确实现。

## 先定义状态作用域

每个状态值必须有且只有一个明确作用域：

| 作用域 | 例子 | 重置边界 |
|---|---|---|
| 整局 `ROUND` | 当前回合、剩余时间、胜负已锁定 | 新一局开始前清零 |
| 队伍 `TEAM` | 队分、阵营门、团队资源 | 换队、离局或新回合 |
| 玩家 `PLAYER` | 角色能力、个人检查点、个人收集 | 重生是否保留需显式说明 |
| 章节 `CHAPTER` | 当前章、局部目标、一次性教学 | 换章、回退或重进 |
| 对象 `OBJECT` | 道具归属、是否交付、生成代次 | 回收、销毁、重新生成 |
| 会话 `SESSION` | 社交交互占用、临时外观/文字 | 离开活动、掉线或离局 |

同一信息不要同时由多个无主变量表达。例如“门是否开”应由一个权威状态决定，灯、声音、门体和 UI 都消费它，而不是各自维护可能分叉的布尔值。

## 状态与转换表

任何带状态的机制先填两张表。

状态表：

| 状态名 | 作用域/所有者 | 初始值 | 谁可读取 | 谁可修改 | 场景反馈 | 重生/换章/新局处理 |
|---|---|---|---|---|---|---|

转换表：

| 来源状态 | 事件/条件 | 防重复条件 | 原子修改 | 玩家反馈 | 延迟/取消 | 失败恢复 | 目标状态 |
|---|---|---|---|---|---|---|---|

“原子修改”指本次转换必须一起成功的状态与对象变化。例如计分时应把资源标记为已消费、增加分数并关闭重复入口视作一个事务；不能先加分、过几帧才销毁资源，给重复触发留下窗口。

## 八条可靠性不变量

1. **单一所有者**：每个可变状态有唯一权威来源；显示件不反向推断真值。
2. **幂等**：完成、计分、领取、开门和存档事件重复触发不会重复发奖、生成或越级。
3. **可取消**：回合结束、换章、失败或离局会停止仍在等待的计时器、运动、追逐与延迟动作。
4. **有代次**：重复生成的对象能区分当前代与旧代，旧对象不能在新局继续触发。
5. **可恢复**：玩家死亡、对象越界、角色掉线或越序后能回到某个完整状态，而不是半完成。
6. **终局锁**：胜负成立后只结算一次，并阻止仍运行的机关、资源或计分改变结果。
7. **新局干净**：连续运行第二局得到与首次加载等价的初始状态，不依赖重启地图。
8. **反馈同源**：声音、灯、动画、文字和空间变化都由同一状态转换驱动，不出现门没开但灯已绿等分叉。

## 1. 检查点与重生

**状态**：`active_checkpoint`、`chapter_state`、必要能力/对象快照、`respawning`。

**转换**：玩家合法进入更后检查点 → 验证章条件 → 提交检查点与保留状态 → 给出明确反馈。重复进入同一检查点只重放轻反馈或无动作；倒退进入不能覆盖更后进度，除非地图明确允许回退。

**恢复**：死亡/越界 → 暂停该玩家临时操作 → 清理随身临时状态 → 在有效检查点重生 → 恢复需要保留的能力与对象 → 重新定向。对象若不能随玩家重生，必须就近召回或回到可再次取得的位置。

**必测**：检查点触发瞬间死亡、两人不同检查点、越序到后点、重复重生、换章后回退、终点后死亡。

## 2. 一次性门、开关与完成区

**状态**：`LOCKED → OPENING → OPEN`，可选 `RESETTING`。

**转换**：合法输入且尚未完成 → 立即锁住重复入口 → 同步更新门状态/任务进度 → 播放反馈 → 开放路径。多个玩家同时进入时仍只执行一次。

**恢复**：开门动画或延迟中玩家死亡不能把门卡在中间；若允许重置，先清理旧动画/碰撞，再回到完整 `LOCKED`。永久章门在检查点提交后由章节状态重建，而不是依赖门体当前位置。

**必测**：同帧双触发、连续进出、输入对象被移走、动画中换章、新局门体与碰撞是否一致。

## 3. 周期危险与移动机关

**状态**：`DISABLED → TELEGRAPH → ACTIVE → COOLDOWN → TELEGRAPH`，终局可进入 `STOPPED`。

**转换**：每个阶段只安排下一阶段的一次计时；离开玩法状态时取消所有待执行回调并把机关放回已定义的安全姿态。预告、伤害/碰撞与视觉运动由相同阶段状态驱动。

**恢复**：玩家重生不应重新创建一套全局周期；局部个人机关若需重启，要先确认旧代已失效。机关卡住时选择完整安全态或完整起始态，不停在扫掠中点。

**必测**：暂停/结算发生在四个阶段中的每一个时刻、多人同时受击、快速重生、第二局相位和碰撞一致性。

## 4. 上涨、追逐与全局倒计时

**状态**：`DORMANT → WARNING → PRESSURE → CAUGHT/ESCAPED → STOPPED`。

**转换**：开始条件成立后先给可见预告，再统一启动世界危险与计时；到达终点或被捕获时先锁结果，再停止危险。若只淘汰落后者而非结束全局，明确个人与全局状态的分离。

**恢复**：检查点重生时决定危险是否保持世界进度、回退到章节进度或给予短保护；不能偶然由重新进入触发区复制第二个上涨体/追逐者。

**必测**：启动区反复进入、玩家在预告期死亡、多人不同进度、终点与危险同帧到达、超时、第二局危险初始位置。

## 5. 收集、搬运、护送与任务对象

**对象状态**：`SPAWNED → AVAILABLE → HELD/FOLLOWING → DELIVERED`，异常为 `LOST/RECOVERING`；每个对象有唯一 ID、所属玩家/队伍和生成代次。

**转换**：领取时先确认未被占用，再原子绑定所有者并改变场景反馈；交付时先标记已消费，再增加进度并生成下一反馈。任务完成依据唯一对象集合或权威计数，不根据当前画面上剩余模型猜测。

**恢复**：越界、卡住、所有者死亡/掉线、换章或传送后，对象回到最近合法锚点、移交或重新生成；旧代对象失效。已交付对象不会被召回后再次计数。

**必测**：两人同时拾取、交付区边缘抖动、携带中死亡/掉线、对象被带出章、重复召回、缺一个对象时能否定位。

## 6. 合作角色与交接

**状态**：角色绑定、能力可用、交接对象/路径机会、双方检查点和缺员模式分开记录。

**转换**：A 完成独占动作 → 生成或改变 B 可见的世界状态 → B 使用后推进共同进度 → 回馈 A 或进入会合。交接事件先锁住当前代，避免额外玩家提前消费或重复生成。

**恢复**：任一人重生时恢复到双方都能继续的最近完整交接点；掉线时进入明确降级分支，撤销无法完成的同步等待，并给剩余玩家替代能力、旁路或退出提示。

**必测**：角色抢占、两人同时失误、先到后触发、越序、额外玩家、交接中掉线、恢复后角色权限是否重复。

## 7. 回合、生存与淘汰

**整局状态**：`PREPARE → LIVE → PHASE_n → SUDDEN_END/FINAL → SETTLE → RESET → PREPARE`。

**转换**：统一释放玩家并启动机关；阶段变化先更新权威回合状态，再启停危险/场地；终局条件采用一次性锁。平局、无人存活、无人得分、时间结束和玩家全离开都有明确出口。

**正交状态面**：复杂派对生存不要把模式、难度、场地事件、天气、玩家生命和可选能力合成一个巨型阶段变量。`ROUND` 唯一决定是否允许玩法和结算；`MODE` 在开局提交本轮生命/得分线与候选池；`FIELD_EVENT`、`WEATHER` 各有选择、预告、生效、清理与代次；每名玩家的 `PLAYER_LIFE` 只负责活跃、重生、淘汰和观战。跨面交接只写明确事件，例如 `ROUND_LIVE` 授权事件选择、`PLAYER_COUNT_CHANGED` 请求终局检查，不能让天气或复活链直接写胜利。

**入口与无输入合同**：记录何时取得控制、何时开始计时、谁能选模式、房主缺席如何继续、可选弹窗能否关闭，以及不输入时的唯一预期。无输入不能绕过契约时长取得胜利、在首个可读预告前遭遇不可避免失败，或无限卡在房主/礼包/教程等待；刻意挂机/放置型地图需明确安全等待、有效循环与退出。

**清理**：停止计时器和机关，清除伤害、生成物、淘汰/观战标记、临时能力和阶段地形，重置出生保护，再开始下一局。不要在 `SETTLE` 期间允许旧攻击或资源改变排名。

**必测**：取得控制后完全不输入、奖励/教程弹窗不操作、房主缺席或不选择、最后两人同帧淘汰、终局时仍有投射物/移动危险、回合中加入/离开、随机场地与天气最坏组合、结算中重生、连续两到三局。

## 8. 积分、资源与热点

**状态**：队伍/个人分数、资源 `AVAILABLE/HELD/SCORED/COOLDOWN`、热点阶段和终局锁。

**转换**：资源领取、掉落、得分与刷新分别有所有权检查；得分动作原子消费资源并更新分数。达到分数线和时间到达同帧时必须有已定义优先级；热点迁移先关闭旧计分，再开放新热点。

**恢复**：持有者死亡/掉线时按规则掉落、返还或作废；新局清空分数、资源代次和热点计时。追赶机制读取落后状态但不能重复叠加。

**必测**：多人同时得分、资源在边界反复进出、终局同帧、领先者掉线、刷新点被占用、第二局分数与热点。

## 9. 顺序谜题与组合机关

先区分两种结构：课程型让多个站点共享一个规则族并逐步改变变量；合集型可以更换局部规则，但复用同一房间状态接口。不要用全局一句规则掩盖合集型各房间的局部教学责任。

**状态**：房间/站点 `LOCKED/ENTRY/OBSERVE/INPUT/RESULT/COMPLETE/RESET`，当前步骤、已确认输入、错误/冷却、提示级别、完成锁、检查点提交和重置代次。

**转换**：进入时先建立安全观察和当前规则；合法输入只推进一个确定步骤并给即时反馈；错误输入进入可诊断状态，再按规则保留部分进度或完整重置。完成时先锁住输入并原子提交本单元，再开放出口/检查点，避免继续点击越过下一阶段。

**提示**：延迟提示只在当前房间活跃且未完成时运行。提示从“观察什么”到“关系是什么”再到“下一步动作”逐级加深；有效进展、完成、离开与重置必须取消旧回调，重复提示不得叠加状态或奖励。

**恢复**：重置先取消旧反馈、提示计时和延迟动作，再清空输入、恢复对象与门体；离开或死亡回到当前单元可解初态。两名玩家同时输入要么排队、要么按明确同帧规则处理。长合集每单元完成后再提交检查点，把失败损失限制在一个房间。

**必测**：入口无输入、双输入同帧、错误后立即正确、提示超时与进展同帧、完成动画中重置、检查点恢复、离开再进入、越序传送和多人看到的状态是否一致。

[《case-007》](exemplars/case-007.md)的代码可证明八个层级入口计时器、八组提示事件、逐层存档/传送及多种异构题芯共同存在，支持“合集复用接口”的设计；本次没有完成任何谜题，不能证明其提示、复位和传送实际可靠。

## 10. 叙事事件与场景变体

**状态**：事件未触发/播放中/已完成、控制模式、场景版本、当前目标、关系值、选择历史、玩家控制权、可跳过标记和章节存档。不要让镜头、NPC 显隐、目标文字和好感 UI 各自维护一套可能分叉的“剧情进度”。

**转换**：进入门槛且前置满足 → 锁住重复播放 → 安全安置玩家/相机并进入明确控制模式 → 播放/接受选择 → 原子提交场景、目标、关系、选择历史和存档 → 关闭旧指引 → 归还控制并发布新指引。环境、灯光、角色、路线、任务和 HUD 应在同一提交点切换。

**反馈时序**：输入后立即确认；1–5 秒内用镜头/对白确认语义；下一个节拍用场景人口、设施、路线、目标或关系至少改变一项；远期分支再读取选择历史。若只有结局文字不同，中途选择很难被玩家相信。

**恢复**：演出中死亡、离开、跳过或断线时选择“回到演出前”或“提交演出后”之一，不能留下半变场景。重复游玩若跳过演出，仍保留必要目标和状态反馈。

**必测**：多人不同时间进入、选择同帧重复输入、演出中死亡/掉线、跳过、传送越序、归还控制后的方向、回访旧场景、重新加载和结局后控制权。

[《case-017》](exemplars/case-017.md)前段观察到固定镜头/自由控制切换、两次选择、人群与电梯状态变化、目标改写、空间指引和 4% 好感持续；发布代码另有多组命名镜头、好感 UI、任务事件和结局成就。它证明这些系统可以共同出现，但没有验证死亡、跳过、回访、重进或完整结局，仍不能照搬其事件顺序和数值。

## 11. 社交交互与临时占用

**状态**：活动台 `FREE/OCCUPIED/COOLDOWN`、占用玩家、临时外观/文字/召唤物和换景位置。

**转换**：进入时确认空闲并绑定玩家；完成、主动离开、超时、远离或掉线均释放占用。多人活动按容量记录成员，不用单一布尔值导致后来者覆盖前者。

**恢复**：换景或回到中心时清理只属于上一场景的临时状态；永久偏好与本次会话效果分开。活动被占用时给后来者可见反馈和其他可做的事。

**必测**：占用者挂机/掉线、多人同帧进入、超时释放、换景返回、临时效果是否污染别人或下一次进入。

## 12. 经营生产与升级事务

**状态**：资源余额/容量、货物或批次 `ORDERED/STORED/WIP/READY/HELD/STOCKED/SOLD`、工作站 `IDLE/PROCESSING/READY/BLOCKED`、货物唯一位置/所有者、领取权、升级等级、必需解锁集合、目录完成锁和阶段目标。显示模型、库存文字和总进度都读取权威记录，不从彼此反推。

**转换**：订货、入库、启动生产、领取、上架、出售与结账都先验证来源、目标容量、归属和批次代次，再原子修改两端；启动生产时扣除输入并创建唯一批次，完成时只把当前批次标为可领取。升级先验证成本和上限，再一次性扣费并切换能力/外观。目录进度由稳定解锁 ID 集合复算；完成谓词成立时原子锁定完成快照，再关闭未提交事务并启用唯一结算/出口。

**角色生命周期**：员工按 `IDLE → CLAIM → WORK → HANDOFF → IDLE` 运行，顾客按 `ARRIVE → CHOOSE/SEAT → CONSUME → PAY → LEAVE` 运行。任务目标失效、无货/无座、等待超时、玩家离开、终局或重载都必须释放占用和孤儿订单；自动化与玩家手动操作不能同时消费同一批货。

**恢复**：玩家离开或工作站销毁时决定批次暂停、结算或退还；多人同时购买/领取只能有一个成功。加载时先禁止交易和胜利，清理默认/旧代对象，恢复站点、解锁、库存与队列，复算目录和容量，最后恢复交互与出口。权威保存者缺席、旧版本字段、半完成订单和“新局”都要有明确分支。无法可靠持久化时，把所有状态限定为单局并在离局清理。

**必测**：双人同时领取/上架/结账、容量已满、扣料后中断、加工中升级、顾客或员工目标失效、终点与最后一次解锁同帧、加载后目录/世界/终点不一致、权威保存者缺席、资源不足、最高等级重复购买、重进和第二局经济清零。

## 13. 随机选择与程序变化

**状态**：当前代次、候选集合、已选结果、预告、有效期和重抽条件。

**转换**：每代只选择一次并发布给所有受影响玩家；候选先经过可解性/公平过滤。重复触发读取既有结果，不在不同客户端或玩家路径上各抽一次。

**恢复**：回合/章节结束使旧代失效，取消其计时与对象；重抽必须有明确事件和新代次。任何候选组合都保留至少一种可行反应。

**必测**：极端候选、连续相同结果、多人同时触发、延迟玩家、旧代对象晚到、重置后是否重新抽取。

## 14. 载具生成、占用与回收

**状态**：载具 `AVAILABLE/OCCUPIED/ABANDONED/RECOVERING`、驾驶者、合法区域、最后安全锚点和生成代次。

**转换**：占用先检查车与玩家都未绑定；离车、翻车、静止超时、越界、驾驶者死亡/掉线触发回收。重新生成前旧车失效，防止地图累积多辆可触发副本。

**恢复**：优先回到不奖励捷径的最近安全锚点，并恢复玩家能力、镜头和速度状态；终局和新局销毁或归位全部载具。

**必测**：多人抢车、车在触发区弃置、越界与终点同帧、驾驶者掉线、旧车迟到和连续回收。

## 15. 累计输入与能力成长

**状态**：原始输入计数、夹紧后的权威成长值、当前能力档位、检查点快照、输入去抖/冷却与终局锁分开记录。玩家显示、成就和实际移动参数都读取同一个成长值，不互相推断。

**转换**：合法输入且当前局可成长 → 先通过落地、冷却或动作边沿去重 → 原子增加计数并夹紧上限 → 更新派生能力 → 只在跨过反馈阈值时播放强反馈。连续值不必每次都创建新 UI、声音或计时器；档位用于表达里程碑，不替代底层权威值。

**恢复**：到达检查点时原子提交位置与成长快照；死亡后按设计选择保留、回退到快照或完整重算，并让能力、UI、成就提示和相机一起恢复。冲线、离局和新局取消旧能力修改、输入监听与延迟反馈；不能让上一局的速度或体型留到下一局。

**空间耦合**：至少在最低、中段和最高能力三档分别标定跑道宽度、转弯半径、落点长度、刹停距离、机关窗口和跟随相机。若最高档只能靠扩大整段空地才能稳定通过，优先降低上限、使用分段映射或让后段空间语法随档位改变。

**必测**：长按/连按/空中重复事件、同帧多次触发、到达上限后继续输入、检查点触发瞬间死亡、能力更新与落点同帧、终点后继续输入、重进和第二局。此模式由《case-012》的元数据与归档结构启发，但其精确去抖、上限和继承行为未还原，所有数值都需独立验证。

## 16. 阵营推理、会议与投票

**状态**：回合代次、私密角色/阵营、阶段、存活与淘汰名单、公共任务/事件、个人合法信息、报告锁、讨论计时、投票资格/选票和多阵营胜利谓词。公共世界只能读取规则允许公开的派生状态，不能从角色变量直接生成他人可见颜色、出生差异或日志。

**转换**：分角完成后才开放场上动作；合法报告先原子锁定场上阶段、取消或冻结任务/攻击/占用，再集合玩家并打开讨论。投票提交校验资格、阶段、玩家、代次和未投状态，每人每轮最多一票；解析平票/弃权/淘汰后先更新名单与权限，再在声明时点检查所有阵营谓词，最后回场或锁终局。

**恢复**：角色掉线时释放其任务、事件、选票、冷却和占用，按合同重分配、中立化、机器人接管或安全终止；淘汰者立即失去所有未声明的结果修改权限。终局清除私密 UI、报告锁、选票、尸体/事件对象、任务代次和延迟输入；第二局重新分角，不能沿用旧阵营或观战权限。

**必测**：重复分角、同时报告、报告与场上攻击同帧、会议开始后旧任务完成、重复/修改/未投和平票、行动角色掉线、淘汰者尝试报告或投票、旧私密动作晚到、多阵营谓词同帧与连续两局。必须在目标人数检查身份泄露、无效会议时间和终局可解释性；单人机器人只能证明流程可达。

## 17. 可破坏目标、依赖结构与奖励提交

**对象状态**：每个可毁目标拥有稳定 `target_id`、所属房间/组、生成代次、合法伤害来源、剩余耐久或离散阶段、碰撞版本和一次性提交锁。推荐最少区分 `INTACT → DAMAGED → CRITICAL → COMMITTED_DESTROYED`；视觉裂纹、材质、音效、碎片和 UI 都从该状态派生。

**转换**：命中事件先验证主循环处于可操作状态、目标属于当前代、来源合法、当前未提交且本次物理输入尚未消费，再原子推进伤害。达到完成条件时一次提交“目标/房间完成锁、碰撞切换、依赖结构结果、奖励或分数、章节/出口检查”；不能先发奖再等待销毁，也不能用场景中当前可见模型数量反推权威完成。

**依赖图**：地板、天花、门、支撑、遮挡或奖励容器的变化写成显式有向边：`前置目标集合 → 一次结果`。提交前检查循环、重复依赖和共享件所有者；同一结构被多个房间引用时只有一个权威组负责销毁或重建。玩家正在依赖面上、下方或唯一退路中时，先执行预告、安全搬离、延迟或已声明的失败/恢复分支。

**恢复**：死亡、检查点、换章和重进明确选择完整重建、保留已提交结果，或恢复到一个一致快照；未提交的半损坏状态不能与完整碰撞/完整奖励随机组合。碎片、持续伤害、迟到命中和延迟销毁都带代次，终局或重置后失效。重复局开始前恢复目标、碰撞、依赖面、奖励锁与反馈，不只换回模型。

**性能与清理**：每个视区记录同时可受击目标、活跃伤害监听、动态碎片、粒子/音效、碰撞切换和延迟回调峰值；碎片声明上限、寿命、碰撞策略与回收。静态表皮可按证据合并，仍需独立受击或换态的对象保留状态边界。

**必测**：同一物理输入产生多次命中、多人同帧最后一击、奖励重复、目标完成与终局同帧、玩家站在依赖面上、共享依赖被两组提交、部分破坏后死亡/检查点、碎片越界、旧代命中晚到，以及第二/第三次进入。现有 [《case-002》](exemplars/case-002.md)只证明相关房间与规则词汇存在，没有实际验证这些不变量。

## 逻辑预算

视觉实例多可以形成场景，逻辑实例多通常增加故障面。对每个系统记录：

- 持久状态数与作用域；
- 事件入口数、条件数和动作扇出；
- 同时运行的计时器、运动体、生成物和动态灯；
- 每次重生、换章、终局和新局需要清理/重建的对象数；
- 与其他系统共享或交叉写入的状态。

优先用一个权威状态驱动多个显示件，而不是复制逻辑。重复装配中的灯、门板和提示可以很多，但负责推进进度的触发链应尽量少而明确。任何跨系统互写都列出优先级和冲突处理。

## 能力落地检查

将抽象逻辑映射到组件前逐条填写：

| 抽象事件/条件/动作 | 当前组件或机制 | 证据等级 | 可写字段/连接 | 不支持时的降级 | 人工验证 |
|---|---|---|---|---|---|

- 只有目录或已解码地图证明存在的触发、动作和属性才能进入实施清单；
- 组件“看起来像按钮/门/计时器”不证明它能提供需要的事件、比较或重置；
- 内置行为无法配置时，按默认行为设计并列为人工验证，不臆造速度、周期、长度或联动；
- 无法实现的分支优先简化主循环、改为空间反馈或标记需用户选择，不用未知字段赌运行结果。

## 整局验证矩阵

至少覆盖：首次加载、正常完成、重复触发、多人同帧、越序、死亡/重生、对象越界、玩家掉线、允许时的中途加入、超时/平局、终局同帧冲突、第二局和第三局。对每一格记录预期状态、实际状态、残留对象、仍运行的计时器/机关和玩家可见反馈。

只有正常路径成功不算闭环。连续两局结果一致，也只能证明已测组合；未支持的玩家数、能力、网络条件和组件默认行为仍作为未知项保留。

## 机器可读状态审计

复杂状态图把设计账本保存为临时 JSON，并运行 `scripts/audit_state_plan.py <plan.json>`。账本至少包含：

- `primary_type/secondary_type`：与总设计账完全一致；主类型必填，次类型没有时为 `null`，不能用省略类型来逃避专项异常场景；
- `stage`：`design` 允许场景为 `planned`，`predeploy` 不允许仍有只计划未测试的场景；
- `lifecycle`：`single_run` 或 `repeatable_round`；后者必须有 `rounds` 功能与可回到初始状态的重置路径；
- `states`：名称、作用域、所有者、是否终局、是否重置；
- `variables`：唯一名称、作用域、所有者、初始值和重置策略；
- `transitions`：来源/目标、事件、守卫、幂等或重复策略、原子修改、反馈、清理、取消延迟和终局锁；
- `features`：按实际选择 `multiplayer/checkpoints/spawned_objects/timed_logic/rounds/scoring/cooperative/narrative_events/social_occupancy/economy/managed_actors/persistent_world/random/vehicles/destructibles`；
- `scenario_matrix`：脚本会同时按主类型、次类型、混合交接和功能自动要求异常场景，状态为 `planned/tested/not_applicable`，不适用必须写理由。体育即使没显式添加“计分”功能也不能漏掉死球/反向入门，音游不能漏掉静音/延迟，潜行不能漏掉警戒恢复；功能列表用于叠加对象、计时、持久化等正交风险，不代替类型。

最小的可重复回合骨架示意：

```json
{
  "schema_version": 1,
  "primary_type": "survival",
  "secondary_type": null,
  "stage": "design",
  "lifecycle": "repeatable_round",
  "initial_state": "PREPARE",
  "features": ["rounds", "timed_logic"],
  "states": [
    {"name": "PREPARE", "scope": "ROUND", "owner": "ROUND_CTRL", "terminal": false, "reset": false},
    {"name": "LIVE", "scope": "ROUND", "owner": "ROUND_CTRL", "terminal": false, "reset": false},
    {"name": "SETTLE", "scope": "ROUND", "owner": "ROUND_CTRL", "terminal": true, "reset": false},
    {"name": "RESET", "scope": "ROUND", "owner": "ROUND_CTRL", "terminal": false, "reset": true}
  ],
  "variables": [
    {"name": "ROUND_PHASE", "scope": "ROUND", "owner": "ROUND_CTRL", "initial": "PREPARE", "reset_policy": "set PREPARE"}
  ],
  "transitions": [],
  "scenario_matrix": {}
}
```

示意中的转换和场景矩阵故意留空，不能通过校验；它只展示字段。运行脚本 `--example` 可查看完整有效示例，`--self-test` 会同时验证有效图并拒绝缺终局锁、不可达状态、断裂重置路径和部署前仍未测试的场景。脚本能证明图可达、终局锁、重置路径和场景覆盖声明自洽，不能证明组件目录支持实现，也不能替代实际多人、掉线和连续回合试玩。临时状态账本不打包进技能。
