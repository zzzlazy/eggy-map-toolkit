# 千件级地图的性能与降级预算

目标不是减少实例数，而是让每个实例只承担必要成本。高完成度场景可以有数千个可见基础件，但不应让每块表皮同时拥有独立碰撞、投射阴影、动态运动、透明和逻辑。

## 证据边界

- 《case-005》的发布缓存包含 6,455 个批加载单位、动态网格与批量合并映射；大量单位关闭投影或物理，说明高密度需要职责分层。
- 《case-020》的 2,342 个批加载单位中，约 93.8% 明确关闭物理、约 95.8% 关闭投射阴影；窄植被词汇负责景观，少量曲面、灯、传送与镜面负责交互或焦点。
- 《case-012》只有 342 个批加载单位和 20 种模型路径，但元数据字段 `eca_trigger_count=1215`，并有多档成长成就与 `use_archive=1`；它证明低渲染数量仍可能是逻辑重图，不证明同时活动逻辑数量、归档内容或运行性能。
- [《case-013》](exemplars/case-013.md)入口初载曾显示约 3 FPS，清空对话并等待后恢复到 60 FPS；它只证明冷进入瞬态与稳定视区必须分开记录，不证明楼内峰值、归档总量与帧率之间存在单一因果。
- [《case-002》](exemplars/case-002.md)以 30 种模型路径展开 7166 个批加载单位并记录 6645 条批合并映射，但取得控制后间隔数分钟的三张画面仍只有约 2–3 FPS；它证明窄词汇、批合并记录和等待加载都不能替代真实稳定视区与首次交互测试。未测同机基线、完整房间或运行剖面，不能把低帧单因归到单位总量、动态网格、逻辑或模拟器。

这些是发布运行时数据，不能直接换算为编辑器组件配额、帧率或目标设备上限。合并、裁剪和批加载属于当前版本与发布管线行为；只有目录、实际发布审计或目标设备测试能证明它们可用。

## 给实例分配成本角色

每个组件除设计层外，再选择主要成本角色：

| 成本角色 | 典型内容 | 默认策略 |
|---|---|---|
| `VIS_STATIC` | 墙皮、岩片、远景轮廓、铆钉、植被 | 无物理；非焦点少投影；静态 |
| `COL_PROXY` | 地面、墙、护栏、区域边界的简化碰撞 | 形状连续、数量少、与表皮边缘一致 |
| `FOCAL_SHADOW` | 近景地标、角色互动台、少量主结构 | 只在关键镜头保留必要投影 |
| `DYNAMIC_MECH` | 转盘、移动台、门、危险体、载具 | 限制同时激活数；记录扫掠和休眠状态 |
| `TRANSPARENT` | 水、玻璃、雾片、半透明 UI/材质 | 控制重叠层和屏幕覆盖；不做无意义叠片 |
| `LIGHT_FX` | 动态灯、投影灯、粒子、全屏特效 | 集中在状态/焦点；远景优先静态或无投影替代 |
| `LOGIC_TIMER` | 触发、计时、比较、循环回调 | 一个权威状态驱动多个表现，离开状态及时取消 |
| `SPAWNED` | 道具、资源、投射物、随机物、临时角色 | 有容量、所有者、代次、回收和终局清理 |

一个对象可能有多个真实成本，但必须指出谁是主要成本和哪些能力被关闭。把所有装饰默认归为“全功能”属于未完成设计。

## 不只看全图总数

同时记录以下口径：

1. **全图规划展开数**：用于完成度、命名和部署规模；
2. **峰值可见数**：一个关键镜头/视区同时进入画面的实例；
3. **峰值碰撞数**：玩家附近需要参与物理查询的代理与动态碰撞；
4. **峰值投影数**：同一镜头可能投射阴影的实例与灯；
5. **峰值动态数**：同时移动、旋转、动画或更新的机关/物件；
6. **峰值透明覆盖**：同一屏幕区域的透明层、粒子和雾；
7. **峰值逻辑数**：同时活动的计时器、循环、触发监听和生成物；
8. **切换峰值**：高速移动、传送、换景、重生或阶段变体时新加载/显隐的内容。
9. **状态/触发复杂度**：持久变量、事件入口、条件、动作扇出、检查点快照和需要在终局/新局清理的系统；它与可见实例另行预算。

全图有 5,000 件但每个视区只见一部分，可能比 1,000 件全部堆在同一透明、动态、投影镜头更稳定。反过来，“总数低”不能证明没有卡顿。

视觉与逻辑是正交成本：数千个静态无碰撞表皮可能主要受可见性、材质和批处理影响；几百个渲染单位也可能被高频输入、变量更新、计时、存档或动作扇出拖慢。设计总账要同时给出可见/物理峰值与状态/触发峰值，不能把 ECA 总数直接当成帧内活动量，也不能只看渲染单位数。

## 视区性能账本

按出生首屏、章节转折、机关高潮、竞技场全景、社交主景、换景落点和终点建立：

| 视区/最坏状态 | 可见展开 | 碰撞代理 | 投影件/灯 | 动态机关 | 透明/粒子层 | 活动逻辑/计时 | 生成物上限 | 目标设备结果 | 降级顺序 |
|---|---:|---:|---:|---:|---:|---:|---:|---|---|

数字来自设计展开和实际测量，不用发布批加载单位代填。每个关键视区至少把 `冷进入最低值/持续时间`、`稳定后值` 与 `交互或多人最坏值` 分开；等待加载后恢复不能抹掉玩家已经取得控制时的卡顿，初载低谷也不能冒充整段稳定性能。没有测量能力时仍记录相对峰值、明显卡顿、加载停顿、输入延迟和视觉异常，并标记未知。

## 机器可读性能账

总设计账与参数化装配完成后生成模板：

```bash
python3 scripts/audit_performance_plan.py \
  design-plan.json assembly-plan.json \
  --template --output performance-plan.json
```

只有主类型时，也可让类型种子同时输出 `--performance-output performance-seed.json`。模板会建立一条 `GLOBAL_WORST_CASE` 和每个实际区域各一条最密视区记录，从展开结果反算 `source_instance_upper_bound`、可见候选上限、成本角色、构成来源和设计职责。它只给候选上限，不会把整个区域误报为同屏可见，也不会伪造帧率。

根字段包括：

| 字段 | 说明 |
|---|---|
| `stage` | `design/review/predeploy` |
| `design_complexity_snapshot` | 总设计账 `complexity_budget` 的原样快照；峰值或降级顺序变化后旧账立即失效 |
| `global_cost_totals` | 本次展开的全图总数、区域、成本角色和构成来源，不手填 |
| `target_context` | 版本、设备、画质、最大目标人数、测量能力、可重复路线和验收合同 |
| `view_budgets[]` | 一条全局最坏状态、逐区最密镜头及必要的自定义切换/高潮镜头 |
| `degradation_steps[]` | 与总设计账顺序一致的降级动作、受影响成本、必须保留的玩法职责和复核结果 |

每个 `view_budgets[]` 包含八个计划峰值：`visible/collision/shadow/dynamic/transparent_layer/active_timer/spawned_object/switch_load`。全局最坏状态必须与总设计账完全一致；逐区视图在 `design` 可暂空，进入 `review` 前必须填完。可见峰值不能超过该视图所含区域的可见候选上限，其他空间件峰值不能超过来源实例上限。逻辑与生成峰值仍来自权威状态设计，不能用静态装配件数代替。

`measurement` 把三个阶段分开：

- `cold_entry`：最低帧率、恢复秒数以及取得控制时的主观响应；
- `stable_view`：典型帧率或 P95 帧时间及稳定旋转/移动结果；
- `worst_interaction`：目标人数、机关、生成物和反馈重叠时的最低值或 P95，以及是否仍可控制。

测量状态分为：

- `unmeasured`：只能配 `result=untested`，不能附伪证据；
- `observed`：设备没有数值遥测时，三个阶段分别记录可复现的定性结果与证据；
- `measured`：三个阶段各有至少一个数值，并保留目标设备记录。

验收合同可用 `numeric`，写冷进入恢复上限、稳定帧率下限和最坏交互帧率下限；没有可靠数值时使用 `qualitative`，但要写可观察、可重复的输入响应、迟加载和画面错误标准。不能用 `unknown` 进入部署。

审计命令：

```bash
python3 scripts/audit_performance_plan.py \
  design-plan.json assembly-plan.json performance-plan.json --json
```

`predeploy` 要求总设计账也是 `maturity=final/stage=predeploy`，版本、设备、画质、最大人数、测量能力和测试路线都具体；所有视区必须以 `observed/measured` 得到 `pass`。数值验收只能由 `measured` 结果通过，且脚本会直接比较冷进入恢复、稳定帧率与最坏交互帧率，不能把低于门槛的记录手动标成 `pass`；定性验收则要求三个阶段各有可复现观察。每个降级步骤必须实际测试，或在基线已通过时明确记为 `not_used`；两者都要说明结果/理由。步骤始终显式保留当前装配中实际存在的导航、危险、交互、目标、状态反馈和碰撞职责，不能用降级解决性能后破坏玩法。

审计器能拒绝过期复杂度快照、区域漏测、来源计数漂移、峰值超过装配候选、未测却声称通过、冷进入与稳定值混写、部署前仍未测，以及删除关键职责的降级计划。它不能证明设备记录真实，也不能从组件数量推导帧率；证据仍来自同一次目标设备测试。

## 结构与表皮分离

- **连续表面**：平台、墙、护栏和边界用少量 `COL_PROXY` 覆盖，表皮分缝、铆钉、植被和岩片使用 `VIS_STATIC`；
- **边缘一致**：视觉可站面与真实碰撞边缘必须一致，不能为了减少代理产生空气墙或空气落点；
- **运动范围**：动态机关扫掠区内不放多余装饰碰撞；机关本体以能表达玩法的最简物理形状为准；
- **远景**：不可达建筑、山体、云、草、树和文字不承担玩家永远接触不到的物理；
- **共享代理**：相邻装配体共享碰撞时在密度账本记录净差额，不能既保留各自代理又叠加一个总代理。

碰撞简化必须通过当前版本实测；模型视觉包围盒不能替代真实碰撞证据。

## 阴影、灯光与材质

- 先用主光、环境明度、材质色阶和轮廓遮挡完成大部分空间分离；动态灯只强化状态变化和焦点。
- 投射阴影优先保留给近景角色接触、关键地标和会影响落点判断的结构；密集微件、不可达背景和远景植被默认不投射。
- 同一灯组照亮同一语义区域；不要给每个墙跨、铆钉或植物单独配动态投影灯。
- 半透明水、玻璃、雾片和粒子检查叠层与屏幕覆盖，尤其避免多个大透明面重叠、全屏粒子叠加和强光遮住路线。
- 发光材质可表达能量或方向，但不能假设它等同于廉价灯光；实际性能仍以目标设备为准。

## 动态机关与逻辑

- 按章节、回合阶段或玩家邻域启停机关；不可见且不影响世界状态的动态体不持续更新。
- 周期机关由一个权威节拍驱动同组表现，避免每个装饰件都有独立计时器。
- 生成物声明同时存在上限、寿命、越界回收、旧代失效和终局清理；没有上限的掉落物、投射物或资源不进入成品设计。
- 可破坏目标把静态框架、受击状态件、碰撞代理和碎片池分开；碎片、裂纹、音效和奖励只消费一次权威提交。同屏多击、连锁依赖面、碰撞切换与终点出现是一个组合峰值，不能只用静止大厅帧率代表。
- 重生、传送、换景和新局前取消旧计时器/运动，防止性能随游玩时间或回合数持续下降。
- 多人地图测试最坏玩家数下的独立物件、技能、投射物和 UI/特效，不用单人帧率代表多人。

## 分区、遮挡、合并与裁剪

- 长图按章节/视区编组，使相邻场景接口明确；转折、门洞、高差和雾可以同时服务构图与可见范围控制。
- 社交或开放图按地标簇组织，不让所有大型场景从中心一览无余；远景主轮廓保留，微细节按距离降级。
- 重复静态表皮优先评估合并、实例化或动态网格，但只有当前管线证据支持时才写为实施方案。
- 合并前先删除重叠、不可见背面和无职责实例；合并不能修复错误碰撞、透明排序、过多材质或错误状态切换。
- 需要单独显隐、换材质、移动、破坏或状态反馈的对象不要盲目合并；按功能边界拆组。
- 远裁剪先作用于小细节与不可达背景，不裁掉主地标、路线开口、危险预告和状态反馈。

## 不同类型的峰值场景

| 类型 | 必须测的最坏场景 |
|---|---|
| 短竞速 | 高速穿过密集转折、多人聚集、连续机关与终点特效同时可见 |
| 章节挑战 | 最大场景揭示、跨章切换、重生回看旧章和长时间游玩后的累积 |
| 机制/解谜 | 全部输入/输出反馈亮起、运动件组合、反复重置后的残留 |
| 合作 | 目标人数同时触发能力、交接物和双侧场景都活动 |
| 叙事/探索 | 场景变体切换、演出镜头、环境灯/粒子与角色同时更新 |
| 生存/淘汰 | 满员、最多危险/投射物、场地收缩和终局反馈重叠 |
| 积分/争夺 | 满员热点、资源/攻击/比分反馈同屏和热点迁移瞬间 |
| 社交/展示 | 主合影点满员、镜面/景深/粒子/灯光和换景回流 |
| 经营/模拟 | 全部工作站生产、容量满、多人领取和大量资源生成 |
| 纯音游/节奏演出 | 最高音符密度、双通道提示、判定/连击反馈、多人分轨和暂停恢复同帧 |
| Boss/PvE 战斗 | 满员、最大攻击组合、预告/投射物/受击反馈、阶段换挡和玩家倒地重叠 |
| 防守/塔防 | 最多敌人、全防御激活、路径重算、漏怪/核心反馈和波次切换同帧 |
| 潜行/渗透 | 最多传感器警戒、多人被发现、搜索目标、环境换态和撤离解锁重叠 |
| 回合策略 | 全棋盘状态显示、最大合法目标集、连锁解析、旁观 UI 和回合换手 |
| 体育对局 | 满员争球、对象轨迹/持有反馈、界外/得分判定、看台和比分效果同屏 |
| 创造沙盒 | 作品预算上限、多人预览/选择、批量保存或加载、测试切换与撤销清理 |
| 阵营推理 | 满员分散于场上、多个任务/事件占用、报告冻结、会议集合/选票、淘汰视角与私密 UI 同时切换 |

启用 `destructible_world` 时，不论主类型是哪一个，都额外测：首次命中、目标受损换态、多目标同帧、最后目标触发依赖结构、碎片峰值、奖励/出口提交、部分破坏后恢复和第二次进入。需要独立变化的可毁件不能为了提高合并数而失去状态边界；静态框架和无交互表皮才优先合并。

## 目标设备测试阶梯

1. **空场/基础地图**：记录设备和版本的基线；
2. **冷进入与取得控制**：从详情/加载进入，记录最低值、卡顿持续时间、何时可稳定输入，以及自动 UI/对话是否掩盖加载；
3. **玩法灰盒**：只保留碰撞、机关和逻辑，确认系统本身成本；
4. **单个最密装配族**：重复到计划密度，验证表皮、碰撞和投影策略；
5. **关键镜头成品**：加载近中远景、灯和 FX，分别记录稳定镜头、旋转和快速移动；
6. **目标人数最坏状态**：同时触发能力、机关、生成物、透明和 UI；
7. **连续流程/多回合**：寻找计时器、对象、缓存或状态残留造成的渐进恶化；
8. **换景与恢复**：传送、重生、章节切换和新局时检查卡顿与迟加载。

若可读取帧率与帧时间，记录典型值、低谷和卡顿点；若只能肉眼观察，至少用同一设备、同一镜头路径和同一人数复测，记录操作反馈、明显掉帧、加载停顿和画面错误。不同设备/画质结果不能混成一个平均数。

## 降级顺序

性能不达标时按对体验影响从小到大处理：

1. 删除完全不可见、重叠、模型内部和无职责实例；
2. 删减远景微件、不可见背面与镜头不会读出的接缝；
3. 合并或减少表皮碰撞，修正重复代理；
4. 关闭非焦点投影、减少动态投影灯；
5. 降低透明叠层、粒子覆盖和非状态性全屏特效；
6. 限制同时活动的动态机关、生成物、循环计时和状态变体；
7. 在有证据时使用合并、分区、裁剪或静态替代；
8. 最后才简化近景装配、主轮廓或章节数量，并重新做主题与路线验收。

不得优先删除路线边缘、危险预告、交互反馈、目标地标、必要碰撞或恢复提示。性能优化后“跑得顺但不知道去哪/发生了什么”仍然失败。

## 交付门槛

成品规格同时包含：成本角色、视区账本、峰值场景、目标设备/人数、测量方法、结果、未知项和逐级降级方案。只有全图总数和一句“会优化”不合格；只在高配单人设备跑过也不能证明目标人数下稳定。
