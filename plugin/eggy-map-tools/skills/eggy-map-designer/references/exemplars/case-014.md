# 匿名案例 case-014

原始名称与身份字段已移除；下文只保留聚合观察、设计推断和证据边界。

## 为什么读它

它是一张不依赖生存压力的纯店铺经营对照：局部循环围绕订货、入库、制作、烘烤、上柜、顾客和结账，长期循环围绕产品、机器、桌位和员工解锁。它适合回答经营图为什么要分开“货物流转、角色队列、全局目录、存档快照和主动胜利出口”，也说明几千个基础实例如何被组织成店铺而不是机关走廊。

## 证据范围

- 观察到店铺首屏、1000 初始金币、`解锁进度 0/25`、产品/机器/餐桌购买位、新手订货目标和局内说明；未实际完成订货、制作、出售、升级、存档或重进。
- 发布缓存展开 3,352 个运行时单位、58 种模型和 1,764 条批合并映射；元数据记录 1,297 个 ECA 触发。847 个可变形方块约占 25.3%，另有 178 个组件组、116 个悬浮文字、30 个碰撞盒、25 个按钮和 23 个座位核心。

## 双层经营合同

```text
局部货物循环
订购原料 → 抓举取货 → 回收入库 → 面团/半成品 → 烘烤
        → 携带成品 → 上柜 → 顾客购买/用餐 → 结账 → 金币

长期目录循环
金币 → 解锁产品/烤箱/柜台/餐桌/员工
     → 容量、并行度、自动化或需求变化 → 新瓶颈
     → 必需解锁集合完成 → 门口终点出现 → 主动离场胜利
```

设计纵切时先让一件货物走完全程，再扩产品树。最小可玩版本也要同时看见当前步骤、来源库存、工作站状态、输出容量、交付结果和下一项可负担升级；不能用一串购买按钮跳过生产。

## 货物、站点与角色状态

| 对象 | 建议权威状态 | 必须恢复的异常 |
|---|---|---|
| 订货/原料箱 | `ORDERED → PICKED → STORED` | 重复领取、丢出边界、储藏满、玩家离开 |
| 原料/面团/半成品 | 类型、数量、容器、批次 | 扣料后制作失败、工作站中断、错误配方 |
| 烤箱/制作台 | `IDLE → PROCESSING → READY → BLOCKED` | 计时中升级、输出满、重载重复产出 |
| 手持成品 | 唯一货物 ID、持有者、携带槽 | 最多携带数、死亡/掉线、重复上柜 |
| 柜台库存 | 产品类型、当前/最大数量 | 满柜、顾客同帧购买、上货后回滚 |
| 顾客 | `ARRIVE → CHOOSE/SEAT → EAT → PAY → LEAVE` | 无货、无座、桌位被删、等待超时 |
| 员工 | `IDLE → CLAIM → WORK → HANDOFF → IDLE` | 多人抢任务、目标消失、终局/重载清理 |

外观、悬浮文字、价格牌、库存条和提示音都读取这些状态；不要从某个蛋糕模型是否显示反推库存。顾客或员工不适用时也要在合同中明确禁用，而不是留一半自动化逻辑。

## 全局进度与胜利出口

- `0/25` 类全局进度是必需解锁集合的投影。权威值应是稳定解锁 ID 集合，计数与 UI 从集合复算；重复购买、读档和补偿不能把数字推过上限。
- 完成谓词应列清哪些产品、机器、桌位或区域是必需，哪些员工/装饰/商业入口可选。可选内容不得意外阻塞胜利。
- 达成条件时先原子提交 `catalog_complete=true` 与完成快照，再关闭未提交购买/生产事务，最后显著启用终点。终点触发本身再做一次幂等终局锁。
- 读档不能只恢复 `25/25`。先清理默认/旧代对象，再恢复机器、桌位、升级、库存和队列，复算目录，最后决定终点显隐；加载中禁止领取、购买和胜利。

## 店铺空间与实例展开

- 用基础件做店铺壳体、柜台、货架、机器厚度、桌椅、产品陈列、管线/电源和招牌；用少量主题件做食物与地标。每个站点建立可复用组件组，统一操作面、状态面、输入/输出和碰撞代理。
- 该案例的 3,352 个单位说明成熟店铺不仅是 25 个购买点：大约四分之一单位复用基础方块，40.8% 使用非均匀缩放，还有大量分组、文字和少量真实碰撞件。展开预算应按店铺壳体、站点族、家具/陈列、导视/UI、角色与逻辑分别对账。
- 操作区优先净空；货架小件和背景默认不参与物理，真实柜台/机器只用少量连续碰撞代理。高密度集中在玩家停留、比较和交付的镜头，不在远景平均撒物。

## 不应照搬与未知

- 不复制主题、产品/价格、箱容量、员工数量、商城/广告/粉丝入口、`0/25` 或玩家 1 存档限制。
- 代码字面量证明生产环节与状态词汇存在，但未验证精确事件顺序、顾客调度、自动化、经济平衡、等待、失败回滚和终局可靠。
- 本案例可作为纯经营结构与实例密度参考；所有产能、成本、顾客速率、目标时长和多人规则必须重新灰盒。

## 视觉与试玩范围

- `[视觉观察]` 详情页将作品描述为制作面包、蛋糕和冰淇淋的清新烘焙店；进入单人后，常驻 HUD 同时显示店铺名、1000 初始金币和 `解锁进度 0/25`，上方可进入员工、说明、商城、金币和粉丝等次系统。
- `[视觉观察]` 出生视野直接展示多座带产品名、价格和库存的机器/柜台，以及双人桌、四人桌、六人桌等扩建位。机器和桌位不是藏在菜单里的抽象升级，而是占据店铺空间的可见目录。
- `[视觉观察]` 新手任务首先要求前往机器订购“面粉（1）+黄油（1）”，目标点约 72 米。局内说明明确“解锁所有产品及餐桌，即可胜利”“胜利点在店铺门口”“本图只读取玩家1的解锁存档”。
- `[视觉观察]` 没有实际到达订货机，也没有完成首次生产、顾客购买、结账、员工招募、升级、保存或重进。因出生到教学机的路线受店铺碰撞与相机方向影响，本次按单样本成本上限停止盲走；不把静态代码当成已试玩时序。

## 代码证据

- `[代码事实]` 归档采用 `preload_batch_unit_data`，展开 3,352 个运行时单位、58 种模型路径和 1,764 条批合并映射；元数据记录 1,621,921 次总操作、1,297 个 ECA 触发。可见场景量和逻辑量均明显高于百件级灰盒，但这些总数不等于峰值同时活动量。
- `[代码事实]` 847 个可变形方块约占 25.3%；另有 178 个组件组、116 个悬浮文字、68 个基础圆柱、63 个地块石头、36 个盘子、30 个碰撞盒、25 个按钮开关和 23 个座位核心。1,367 个单位使用非均匀缩放，521 个至少有一轴不大于 0.25，635 个存在 X/Z 倾斜；基础件通过缩放、姿态、分组与少量主题件构成店铺、机器、家具、食物和导视。
- `[代码事实]` 任务字面量支持一条新手生产链：订购面粉/黄油、抓举取货、回收入库、面粉制面团、制作牛角酥半成品、烤熟、最多携带三个成品、上货到柜台、等待顾客、给用餐结束的顾客结账。字面量还包含“上货成功”“制作成功”“烤制开始/完成”“顾客用餐”“完成结账”等事件名；它们证明系统词汇与环节存在，不证明精确触发顺序或无故障。
- `[代码事实]` 产品目录至少包含奶油面包、牛角酥、甜甜圈、多种蛋糕/挞和冰淇淋；空间对象包含制作台、储藏区、取货处、烤箱、冰淇淋机、柜台、桌位与座位核心。产品站与桌位显示多档价格，部分产品以“一箱（6个）”为库存批次，柜台字面量含 `1/6`，半成品含 `1/3`。
- `[代码事实]` 员工词汇包含总厨、厨师、冰淇淋制作师、搬运工、订货员、收银员和多名服务员；总厨说明负责面团和半成品，另有自动上货线索。顾客存在普通/用餐两类状态。静态字符串不能证明其调度、公平或离场恢复。
- `[代码事实]` 胜利事件字面量为“已达成胜利条件，终点出现在门口”，与 `0/25` 全局解锁 HUD 和说明文字一致；归档另有胜利区域。长期完成条件、终点解锁和实际进入胜利区是三个应分离但同源的状态。

## 蒸馏

- `[设计推断]` 经营图应同时有两个闭环：秒到分钟级的局部工作单 `输入 → 在制品 → 成品 → 上架/交付 → 收益`，以及跨循环的全局目录 `收益 → 解锁机器/产品/桌位/员工 → 新瓶颈 → 完成条件`。只做购买列表会失去劳动感，只做生产链又缺少长期方向。
- `[设计推断]` 每件货物都需要稳定 ID、类型、数量、状态和所有者/所在容器；订货箱、储藏库存、面团、半成品、烤箱批次、手持成品、柜台库存和已售商品不能只靠模型是否可见来猜。每次转移先锁来源与容量，再原子修改两端，失败不得复制或吞货。
- `[设计推断]` 顾客与员工把纯资源图变成排队/容量图：顾客经历到店、选购/落座、用餐、待结账、离店；员工经历空闲、认领任务、执行、交付、释放。二者都要处理目标失效、站点已满、玩家离开、终局和重载，否则最容易留下孤儿订单或永久占用。
- `[设计推断]` `0/25` 一类总进度适合作为长期方向，但不能替代当前订单、缺料、在制品、柜台容量和顾客需求。全局计数必须从唯一解锁集合复算或幂等提交，不能由多个购买按钮各自随意加一。
- `[设计推断]` 胜利点与经营区分离能给玩家一个主动收束：满足条件后先锁定完成快照、停止会改变目录的旧事务，再显著打开门口终点；加载满解锁存档时也要重建机器、桌位、库存规则和终点状态，不能只把进度改成 25/25。
- `[设计推断]` 3,352 个单位不是平均撒装饰：高频方块承担店铺壳体、柜台、机器和家具细分，组件组形成可复用站点，文字和按钮形成操作/状态层，碰撞盒集中在真实接触面。规划经营图时应分别预算“可见空间实例、可交互站点、产品/订单状态和峰值活动角色”。

- 不复制韩式烘焙主题、产品清单、价格、`0/25` 数值、箱容量、员工名称、商城/广告/粉丝入口、胜利门位置或玩家 1 存档限制。
- 本次没有完成实际生产循环；不能宣称任务字面量的排列就是运行事件图，也不能据此判断订单刷新、员工效率、顾客耐心、等待时长、经济曲线或终局可靠。
- 只读玩家 1 存档是明确能力/设计限制，不是多人经营的推荐方案。仍需测试保存快照、加载顺序、非权威玩家投入、权威玩家掉线和干净新局。
- 该案例补齐了纯经营图的首屏、产品目录、局部生产链字面量、员工/顾客角色与长期终点证据；下一张经营样本应优先完成一整轮生产、一次升级和一次干净重进，而不是继续增加同类静态目录。
