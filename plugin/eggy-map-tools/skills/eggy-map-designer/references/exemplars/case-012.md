# 匿名案例 case-012

原始名称与身份字段已移除；下文只保留聚合观察、设计推断和证据边界。

## 为什么读它

它不是高环境密度样本，而是一张“渲染词汇很窄、状态与触发很重”的单规则长图。它适合回答：怎样让同一个玩家输入持续改变能力、怎样把连续数值压成可读里程碑，以及为什么场景实例预算和逻辑预算必须分开。

## 证据范围

- 只有推荐卡片，没有出生区画面或完整试玩；不能据封面判断实际路线、速度上限、复位或镜头。
- 发布缓存包含 342 个批加载渲染单位、20 种模型路径；元数据记录 8,059 次编辑操作、1,215 个 ECA 触发和五档成长成就。它们属于不同口径，都不是编辑器顶层组件数或同时活动逻辑数。

## 构成拆解

- **规则核**：简介把“每次跳跃增加速度”作为唯一承诺；五档成就目标为 3、6、12、24、48，把高粒度成长转成少数反馈节点。
- **稳定基线**：61 段动画围栏、61 根围栏柱、38 条传送带、34 个弹板、28 面气垫墙、26 个果冻蹦床和 21 块大地板构成重复赛道词汇；机关变化发生在熟悉的空间语法上。
- **模块化尺度**：322 个单位采用非均匀缩放，142 个至少一轴绝对缩放不小于 5；位置在 X 轴跨度近千米，支持长距离模块化赛道推断，但不证明真实行进方向。
- **恢复切段**：字符串表出现 14 个存档区域。成长状态与位置检查点必须共同定义死亡后的权威状态，否则速度、成就和关卡位置会分叉。
- **成本分离**：较少可见单位并不等于实现简单；ECA 和操作数提示主要复杂度可能在输入计数、能力更新、档位反馈和异常恢复。元数据 `use_archive=1`，但具体保存内容未知。

## 可迁移设计卡

| 字段 | 应明确的内容 |
|---|---|
| 原始输入 | 哪个动作计数，落地、连按、多人和重复事件如何去抖 |
| 权威变量 | 谁拥有计数/能力值，初始值、上限和更新频率 |
| 派生能力 | 数值如何映射到速度、跳跃、体型或其他能力，是否分段而非无界连续 |
| 反馈档位 | 哪些阈值改变 UI、颜色、声音、称号或路线预期 |
| 空间校准 | 最低、中段、最高能力下的跑道宽度、转弯半径、落点和相机 |
| 检查点 | 死亡后保留、回退还是重算成长；位置和能力必须原子提交 |
| 终局清理 | 冲线、退出、重进和第二局如何取消旧能力、计时与反馈 |

采用 `原始输入计数 → 夹紧后的权威值 → 派生能力 → 少数反馈档位`。先在三档能力下分别标定同一组空间模块，再增加中间成长，不要先让数值无限增长后再用更宽的空地补救。

## 不应照搬与未知

- 不复制 `+5` 公式、成就阈值、彩虹赛道封面、车辆梗、具体关卡顺序或机关数量。
- 没有证据证明输入去抖、最高速度、死亡继承、检查点提交、终点停机和重进重置的实际实现。
- 342 个运行时渲染单位不能证明高画面完成度，也不能否定主题图需要数千个有效基础件；本案例只校准“逻辑密度”和“视觉密度”是两条轴。

## 身份

- `[元数据事实]` 最低与推荐人数均为 1；有效游玩约 876.3 万，中位完成时长约 340.35 秒，元数据 `use_archive=1`，但缓存没有说明具体保存哪些状态。

## 证据

- `[视觉观察]` 只取得推荐卡片：画面把多条高饱和直赛道、方向箭头、标题规则和终段车辆并置，能证明宣传层强调“速度持续成长”，不能证明出生区、实际路线或终点镜头。没有出生区截图，也没有完成整局试玩。
- `[代码事实]` 归档为 47 块、8 字节表项布局；批加载渲染单位 342，模型路径 20 种。规划统计中的 `8,059` 次操作与 `1,215` 个 ECA 触发记录属于元数据复杂度信号，不能当作同时运行的逻辑数。
- `[代码事实]` 高频词汇集中于动画围栏 61、围栏柱 61、传送带 38、弹板 34、气垫墙 28、果冻蹦床 26 和大地板 21；另有 14 个存档区域、10 个放电柱、10 个触碰掉落板、7 个冰地面和 6 个顺时针转盘。
- `[代码事实]` 342 个渲染单位中 322 个采用非均匀缩放，142 个至少一轴绝对缩放不小于 5；单位位置 X 轴约从 `-981.5` 延伸至 `10`，Z 轴约从 `-29.5` 到 `157.5`。这支持“长距离、规则对齐的模块化赛道”推断，不证明玩家按 X 轴单向跑完全程。
- `[元数据事实]` 五档成就目标为 3、6、12、24、48，名称从“速度一颗星”递进到“速度十颗星”；简介宣称每次跳跃增加速度。缓存没有还原精确变量、加速上限或触发顺序。

## 蒸馏

- `[设计推断]` 这张图的主要内容预算不在场景资产种类，而在“同一输入不断改变移动参数”带来的状态演化。设计预算必须把可见实例、持久状态、触发入口和反馈档位分开记账；低渲染单位不等于低系统复杂度。
- `[设计推断]` 规则成长图需要稳定的空间基线。围栏、传送带、弹板、气垫墙和蹦床反复出现，使玩家能把动作结果归因于速度变化，而不是每一关的新机关。
- `[设计推断]` 成就阈值把连续数值成长切成可理解的里程碑。可迁移的是“原始计数 → 受限派生能力 → 少数可见档位”，不是照搬 `+5` 或 3/6/12/24/48。
- `[设计推断]` 14 个存档区域说明长规则训练仍需把失败损失切段；检查点应恢复权威成长状态或明确重算，不能只传送玩家而让速度、成就和路线状态分叉。

- 不复制标题公式、彩虹直道封面、车辆梗、成就文案、关卡顺序或具体机关数量。
- 尚不清楚一次跳跃如何去抖、空中连续输入是否重复计数、速度是否封顶、死亡后速度如何恢复、检查点是否保存成长值以及终点如何清理。
- 该案例证明规则驱动图可以用较少渲染单位承载较多状态与触发设计，不证明 342 个单位足以做高环境完成度地图，也不能作为低端设备性能结论。
- 推荐卡片不是出生区证据；后续若能稳定进入单人模式，应补第一视线、赛道宽度、成长反馈、最快状态下的镜头与碰撞，以及第二次进入是否干净重置。
