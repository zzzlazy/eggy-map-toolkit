# 匿名案例 case-002

原始名称与身份字段已移除；下文只保留聚合观察、设计推断和证据边界。

## 为什么读它

它同时提供三个有边界的参考：一是用房间壳体、标牌、工具和中心焦点建立“盲盒工厂”首屏；二是用窄资产词汇展开数千运行时单位；三是把多个房间组织为可破坏对象、依赖面、积分与出口的状态问题。它也有两条重要反例：常规尺度的工厂不自动成为微缩玩具世界，已有批合并且模型种类少也不自动带来稳定帧率。适合参考可破坏世界修饰器、房间单元、工业室内和密度/性能分账；不适合作为糖果童话、巨物微缩、完整拆除节奏或性能样板。

## 证据边界

- 已观察详情封面/缩略图、规则弹窗、取得控制后的大厅与正常退出；没有挥锤、拆完任何面、进入其他房间、得到积分、到达终点、死亡或重进。
- 归档展开 7166 个批加载单位、30 种模型路径/ID、6645 条批合并映射和 792 个动态网格路径；直接可核对的名称包括无形方块 162、可变形方块 121、方墙 90、公告牌 32、基础圆柱 29、走廊 6。
- 文本出现多个功能房间、“四面墙消失后地板与天花板一起销毁并产豆”、当前积分、锤子档位和终点出现等词。它们支持对象与房间合同，不还原真实事件图或证明事务可靠。
- 三次可控画面仍显示约 2–3 FPS；没有取得稳定高帧证据。不能由全图总量或静态字段单因归责，也不能把“已合并”写成性能结论。

## 玩具语义与微缩尺度是两条轴

可控首屏由米灰墙板、顶梁/灯格、坡道、门框和“大厅”标牌建立常规工业房间；中轴橙色装置、金色蛋仔雕像、玩家手持锤和“拆”技能再说明玩具/盲盒与破坏动作。它支持的是“场所壳体 + 主题焦点 + 可执行动词”的组合。

微缩世界还需要另一组证据：至少两个熟悉日常物比玩家大一个明确层级，并把包装边、桌面、缝隙、卡扣或标签真实转化为路线、遮挡和地形。本案首屏没有这种比例关系，因此设计时分别填写：

```text
TOY_SEMANTICS    哪些轮廓、关节、包装、工具或零件说明这是玩具世界
SCALE_ANCHORS    哪些熟悉物与玩家形成可复述比例
ROUTE_CONVERSION 哪些物件真的成为地形、门槛、遮挡或交互面
MATERIAL_SPLIT   塑料、纸、布、金属、糖晶怎样通过边缘和光泽区分
```

只有第一项成立时称为玩具题材，不称为巨物微缩；只有颜色和玩偶成立时，两者都未完成。

## 可破坏房间单元

把每个房间视为一个带状态的装配，而不是一堆能被随意删除的墙：

```text
DESTRUCTIBLE_ROOM =
  STATIC_FRAME
  + DESTROYABLE_WALL_SET
  + DEPENDENT_FLOOR_CEILING
  + COLLISION_PROXY_SET
  + ROOM_SIGN
  + DAMAGE/COMPLETION_FEEDBACK
  + REWARD_AND_EXIT_PORT

ROOM_STATE = INTACT -> DAMAGED -> CRITICAL -> COMMITTED_DESTROYED
```

最后一个合法目标被处理时，按一次原子事务执行：

1. 验证房间 ID、目标 ID、当前代次、伤害来源和未提交锁；
2. 锁住本次命中与房间完成，避免同帧重复；
3. 更新目标/房间状态并安全切换碰撞；
4. 按依赖图处理地板、天花、门或支撑面；
5. 发放一次奖励并从权威状态更新进度；
6. 播放碎裂/音效/文字并开放下一路径或终点；
7. 把碎片、延迟回调和旧代对象纳入清理。

依赖图不能靠场景中“还剩几个模型”反推。若玩家正站在将消失的地面上，先定义安全落点、预告、延迟或搬离；视觉销毁、碰撞消失与奖励提交的先后必须可测。

## 重复房间如何产生变化

共用壳体、层高、门洞、标牌槽和完成反馈有利于学习；每个新房间只改变一到两个决策轴：

| 变化轴 | 合法变奏 | 失败做法 |
|---|---|---|
| 目标拓扑 | 四周墙、分区墙、承重点、移动目标 | 只把相同墙血量加倍 |
| 工具取舍 | 范围、速度、风险、有限资源 | 付费档位成为唯一合理路线 |
| 拆后用途 | 开新路、露出机关、改变视线、形成回程 | 销毁后只清空画面 |
| 环境压力 | 落物、移动面、时间窗、暴露区 | 无预告地让脚下全部消失 |
| 信息顺序 | 先观察依赖、再选择目标 | 长说明遮住目标与后果 |

视觉 A/B/C 变体不能暗改碰撞或伤害规则。普通墙、必要目标、不可打面和已完成面要通过轮廓、材质、状态灯或受击反馈区分，不能只靠文字。

## 从 7166 件学什么

- 高展开可以来自很窄的模型词汇；房间墙板、框架、标牌和碰撞代理先形成稳定装配族，再由功能名和状态改变房间身份。
- 7166 是全图运行时总账，批合并部分没有逐件语义。新设计仍要按 `房间/走廊/焦点 -> 装配族 -> 静态壳体/可毁状态件/碰撞/反馈/逻辑` 分账，不能给一个大厅挂上全图数量。
- 需要独立受击、显隐、换材质或碰撞切换的对象必须保留状态边界；静态框架、重复收缝和不可交互表皮才适合评估合并。合并数量不是完成度或性能指标。
- 可毁表面和碎片会把逻辑、动态、碰撞与切换峰值叠在同一镜头。目标设备测试至少覆盖冷进入、首次命中、同帧多击、多面连锁、奖励提交、终点出现和第二次进入。

## 不应照搬

不复制标题、房间排列、角色雕像、盲盒造型、4500 豆阈值、锤子档位、广告/商城入口、文字、音乐或具体资产。该案只支持玩具工厂首屏的部分语义、可破坏房间合同、窄词汇高展开和性能反例；不证明糖果/童话/微缩世界、命中手感、耐久平衡、连锁安全、完整路线、终局或重进可靠。

## 身份与证据范围

- `[元数据事实]` 详情页标签为“消除 / 解压 / 可爱”，显示约 38.1 万游玩、4.6 万点赞和 4.5 分；缓存记录 `valid_play=381219`、`like=45807`、`appreciate_num=1120`、`appreciate_score_total≈4.47`、制作时长 221261、总操作 34590、ECA 触发记录 13909。传播与评分只证明候选有较多反馈，不证明完成度、平衡或性能。
- `[视觉观察]` 已观察详情封面与缩略图、规则弹窗、取得控制后的大厅首屏，并通过游戏内退出流程正常离开。没有挥锤、拆完任何墙面、取得豆豆、进入其他房间、触发胜利、死亡或验证第二次进入。

## 首屏与主题边界

- `[视觉观察]` 详情封面用高饱和发光蛋形盲盒、持锤角色和“拆光”大字先承诺“玩具容器 + 破坏动作”；可控首屏则转为米灰工业大厅，主要由墙板分缝、顶梁/灯格、两侧坡道、门框和房间标牌构成。
- `[视觉观察]` 大厅中轴的橙色箱形装置、金色蛋仔雕像、手持锤和“拆”技能共同建立近景动作焦点；两侧“大厅”标牌和对称坡道让最近可达方向可读。玩家仍处于常规走廊尺度，没有超大包装、桌面物或日常物件把角色明确缩小。
- `[设计推断]` “玩具语义”和“微缩尺度”必须分开验收。该样本能部分支持用可辨焦点道具、工具和房间功能把普通厂房变成盲盒工厂，但不能填补糖果、童话、巨物微缩、包装层级或尺度转场证据。
- `[视觉观察]` 规则弹窗占据画面中央，关闭后主动作才可读；右侧还有广告锤入口。可选升级与商业入口不能成为新设计的主任务表达，更不能遮住世界和路线。

## 基础件、分区与性能事实

- `[代码事实]` `preload_batch_unit_data` 可解析出 7166 个批加载单位、仅 30 种模型路径/ID，并记录 6645 条批合并模型映射和 792 个动态网格路径。它证明全图使用窄资产词汇进行大规模展开；不能把 7166 全部归为大厅、玩具美术、可破坏墙面或编辑器顶层组件。
- `[代码事实]` 可直接核对的高频名称族包括无形方块 162、可变形方块 121、方墙 90、简约公告牌 32、基础圆柱 29、点光源 11、走廊 6；另有少量环件、扇形、售货机、游戏机、回收桶、弹簧、相机路径与胜利区域。显式模型记录主要是连续碰撞、房间壳体、标识和焦点道具，批合并部分没有逐件语义，不能由总数补写材质或职责。
- `[代码事实]` 名称与有限文本出现洗衣室、美化间、食堂、休息室、保险库、仓库、包装车间、电力室、组装间、安保室、设计室、展示台和多条走廊；它支持“多个功能房间复用共同壳体/标牌接口”，不证明实际邻接、进入顺序或每个房间都完整可玩。
- `[视觉观察]` 取得控制后约 12:37、12:38、12:41 的三张观察图仍分别显示约 2、2、3 FPS，延迟约 64、148、45；没有观察到恢复到高稳定帧率。低模型词汇、批合并记录和等待数分钟都不能单独证明性能合格，也不能仅凭这些字段确定瓶颈来自可见单位、动态网格、逻辑、灯光、模拟器或其他因素。

## 可破坏房间的代码线索

- `[代码事实]` 规则文字明确地板与天花板不可直接打击，会在四面墙消失后一起销毁并发放豆豆；达到 4500 豆可过关。代码文本还出现“墙板已拆完”“地板与天花板已自动销毁产豆”“当前积分”“游戏终点已出现”等反馈，以及石锤、铁锤、金锤三种伤害档位。
- `[代码事实]` 房间名与“墙板已拆完”反馈重复组合，说明发布内容至少为多个房间保留相似的完成词汇；它支持一种 `ROOM_ID + WALL_SET + DEPENDENT_FLOOR_CEILING + REWARD_COMMIT` 的研究模型，不能证明命中去重、耐久数值、毁坏顺序、碰撞切换、奖励原子性或回档已经正确实现。
- `[设计推断]` 可破坏世界应把视觉壳体和权威对象状态分开。每个房间的墙组拥有稳定 ID 与代次；合法打击只推进一次；最后一面墙提交时原子锁定房间、切换碰撞、处理依赖面、发放一次奖励并更新出口。视觉碎片和音效从提交派生，不能反向决定房间是否完成。
- `[设计推断]` 多房间拆除不应只是重复血量。相邻房间至少改变目标拓扑、暴露风险、工具取舍、先后依赖、移动方式或拆后空间用途之一；壳体、标牌和状态反馈可以复用共同接口。

## 可迁移方法

1. 用 `ROOM_SHELL + DESTROYABLE_WALL_SET + DEPENDENT_SURFACES + STATUS_SIGN + COLLISION_PROXY + REWARD/EXIT_FEEDBACK` 建立可复用房间单元；先验证一个完整事务，再复制到多房间。
2. 让可破坏面拥有完整、受损、临界和已销毁的可读状态；伤害来源、同帧去重、奖励提交与终局优先级由一个权威控制器负责。
3. 把房间壳体与玩具焦点分层：梁、墙板、坡道、门框和标识负责场所；盲盒容器、雕像、工具、零件和包装附着负责主题。仅靠粉色或玩偶不能替代结构。
4. 数千件总账拆回每个房间、走廊、焦点和状态层；批合并只服务静态兼容子件，仍需独立变化或受击的面不能因追求合并而失去状态边界。
5. 把冷进入、规则弹窗关闭后、首次打击、多墙连锁销毁和终点出现分别建成性能视区；若可控状态长期低帧，先减少同屏动态/逻辑/投影/碎片峰值，而不是只报告全图已经合并。

## 不应照搬与未知

- 不复制标题、房间排列、雕像、盲盒外观、拆除阈值、4500 豆、锤子等级、广告/商城入口、文本、音乐、排行榜或具体资产阵列。
- 未实际打击任何对象，不能宣称原作已经解决命中去重、伤害公平、耐久曲线、依赖面销毁、积分重复、检查点、碎片回收、胜利同帧冲突或重进清理。
- 7166 是运行时批加载口径，不是编辑器顶层组件数，也不是任一房间的配额；30 种模型路径只证明词汇窄，不证明每个实例有效。
- 下一张正向玩具/微缩样本仍需可控的完整路线、明确尺度锚点、包装/拼接/材质语法和尺度转场；下一张可破坏样本只接收能低成本完成一个房间并复测第二次进入的作品。
