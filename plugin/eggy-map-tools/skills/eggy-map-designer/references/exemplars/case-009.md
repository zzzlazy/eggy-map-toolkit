# 匿名案例 case-009

原始名称与身份字段已移除；下文只保留聚合观察、设计推断和证据边界。

## 为什么读它

这是一张“少资产词汇、高实例展开、高逻辑密度”的团队积分擂台。它适合回答：基础件如何组合出大尺度竞技场、选装如何与正式计分分离、比分/阵营/能力如何同时保持可读，以及为什么对抗图不能只摆几件攻击机关。

## 证据范围

- 观察到技能选择层、星云圆形主擂台、远端小圆台、红白比分、长倒计时、换技入口及当前技能；单人未发生有效对抗，3V3 公平、得分、复活和终局均未实测。
- 发布缓存有 1,049 个批加载渲染单位、13 种模型路径；元数据记录 3,319 次操作和 990 个 ECA 触发。485 个可变形方块、384 个质量回复电池、125 个可变形圆环约占全部单位 94.8%。

## 构成拆解

- **装配层**：大量薄片、环和方块通过非均匀缩放形成圆形场界、星云表面、轮廓与分区；少量星云平台和圆台提供地标。高完成度来自实例间的几何关系，不来自模型种类。
- **准备层**：玩家先选决斗技，再进入擂台；主场仍提供“换决斗技”入口。选择、提交、换装冷却和返场保护必须分别定义。
- **阵营层**：6 个分阵营出生点与红白比分支持 3V3 结构；颜色首先服务归属和比分，不应被背景主题吞没。
- **计分层**：8 个计数器、死亡文本和简介的 80 分目标形成直接击败计分线索，但精确事件连线未知。得分必须只有一个权威入口，并防止重复死亡事件重复加分。
- **恢复层**：简介声明无限复活，7 个销毁区域与多类触发区提供恢复线索；重生位置、无敌窗、技能冷却和场内召唤物需要原子清理。

## 可迁移状态骨架

`等待 → 选择能力 → 锁定队伍/出生 → 比赛启用 → 击败/得分 → 死亡清理 → 保护性返场 → 达到分数或超时 → 停用伤害与计分 → 结算 → 全局清零`

每条得分事件都记录：事件源、得分队、幂等键、反馈、领先状态、终局检查；每条死亡事件都记录：角色状态清理、携带物/召唤物清理、复活位置、保护窗和重新获得控制。

## 实例预算校准

- 先用少量模型建立 4–7 个装配族，再展开数百到上千个有职责的实例；一百来件通常只够公平灰盒和第一版状态验证。
- 基础件实例要能归入 `场界/接触面/路线与站位/阵营识别/主题纹理/反馈载体`。不可见重叠、无收益碎面和平均撒点不计完成度。
- 逻辑预算单独记 `权威比分、队伍、选装、死亡、复活、计时、终局、清理`；不能用场景件数量冒充系统闭环，也不能用 ECA 数量冒充公平。

## 不应照搬与未知

- 不复制咸鱼题材、星云圆台、技能清单、80 分、公告文本或角色造型。
- 未验证 3V3 真实行进时间、出生视线、刷分防护、追赶机制、练刀台是否干扰正式比分、平局和第二局残留。
- 极窄资产词汇可以形成完整美术，但必须有受控缩放、轮廓层级和性能职责；不能把同一件机械复制到看不见或没有结构价值的位置。

## 身份

- `[元数据事实]` 简介声明 3V3、无限复活、练刀台、计数和 80 分结束，并支持单人游玩；最低与推荐人数字段均为 1，不等于主要平衡目标只有单人。
- `[元数据事实]` `game_time_limit=6000`，完成时长中位数约 1275 秒、平均数约 1390 秒。公开统计为 `play=3910214`、`valid_play=2402547`、点赞 313095；热度只能证明传播，不证明公平。

## 证据

- `[视觉观察]` 详情页显示擂台、友情、童话标签。单人进入前出现决斗技选择层，可见贴贴药水、伙伴炮台、龙卷风、时空跃迁、炸弹崽、百变技能箱、落雷、无敌、雪球滚滚、机械抓钩等候选；选择后进入黑白星云质感的巨型圆形主擂台，远处另有小圆台。
- `[视觉观察]` 局内 HUD 同时显示红白双方 `0:0`、倒计时约 `99:50`、提示“换决斗技”、当前技能“无敌”和“咸鱼”。这证明准备阶段负载选择与主循环分离、比分和换技入口常驻可见；单人没有发生有效对抗，未验证得分、复活或终局。
- `[代码事实]` 归档有 1,049 个批加载渲染单位、13 种模型路径；元数据记录 3,319 次操作、990 个 ECA 触发、占用 14,262。可见实例和逻辑密度都显著高于最小原型，但仍使用极窄资产词汇。
- `[代码事实]` 485 个可变形方块、384 个质量回复电池、125 个可变形圆环合计 994 个，约占全部渲染单位 94.8%。另有 8 个计数器、7 个销毁区域、6 个分阵营出生点、6 个圆台、3 个星云平台、2 个事件触发区、2 个通用触发区和 2 个按钮开关。
- `[代码事实]` 904 个单位采用非均匀缩放，879 个至少一轴绝对缩放不大于 0.25。单位坐标跨越多个远距离簇，支持“主场、练习/选择或逻辑隔离区分开布置”的推断，但静态坐标不能证明每个远端簇的实际用途。

## 蒸馏

- `[设计推断]` 高完成度对抗场可以由少量基础件大规模装配：方块承担大面、边缘和图案，圆环承担轮廓与场界，高频同形道具承担主题纹理或状态表现；少量计分、触发和出生组件负责规则。可迁移的是“结构词汇少、实例展开深、逻辑接口清楚”，不是复制星云圆台。
- `[设计推断]` “选技能”是独立准备状态，不应和正式计分同时开始。设计时至少拆成 `准备/选装 → 队伍与出生提交 → 比赛 → 得分/死亡/复活 → 达标或超时 → 停机/清理`，并决定换技会不会重置位置、冷却或短暂无敌。
- `[设计推断]` 常驻比分、双方色和技能标签把三条信息分开：谁领先、我属于谁、我能做什么。竞技 HUD 优先展示可行动信息；宣传、排行榜或装饰文本不能挤占同一层级。
- `[设计推断]` 80 分和无限复活意味着场地必须同时解决出生保护、返场距离、刷分防护和拖局。高 ECA 数量提示系统复杂度可能主要在技能、死亡、计数与恢复，不能用同等数量的机关替代状态机设计。

- 不复制标题、咸鱼主题、技能清单、80 分阈值、黑白星云纹理、角色造型或公告文本。
- 单人观察不能证明 3V3 的出生公平、命中反馈、比分归属、队友辨识、复活保护、追赶机会、练刀台隔离、平局、断线补位或第二局清零。
- `game_time_limit=6000` 与简介的 80 分终局同时存在；无法仅凭缓存判断超时如何结算，也不能把公开完成时长解释为一局标准时长。
- 1,049 个运行时渲染单位不是编辑器顶层组件数；3,319 次操作和 990 个 ECA 触发也不是同时活动逻辑数。
