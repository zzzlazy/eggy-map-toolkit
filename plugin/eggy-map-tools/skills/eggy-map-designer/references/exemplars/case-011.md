# 匿名案例 case-011

原始名称与身份字段已移除；下文只保留聚合观察、设计推断和证据边界。

## 为什么读它

它把生存压力、背包制作、建筑放置、生产站、岛屿扩张和存档压进同一张混合图。适合回答：经营循环怎样从资源依赖图展开成世界、升级怎样改变下一轮瓶颈、快捷栏/容量/建筑上限怎样进入一致性合同，以及持久化为什么必须先定义所有权。

## 证据范围

- 观察到第 0 天首屏、生命/饱食/口渴/天数、快捷栏、16 格背包、制作菜单和工作台配方；没有实际完成采集、制作、放置、升级、登岛、保存或读取。
- 发布缓存有 1,051 个批加载渲染单位、18 种模型路径、426 条批合并映射；元数据记录 46,749 次操作、23,426 个 ECA 触发。451 个基础方块模型约占 42.9%，其余高频词汇集中于岛屿岩石、树、矿物、水和少量交互/边界件。

## 混合契约

- **主循环**：经营/建造——采集 → 制作/加工 → 放置生产站 → 获得更高阶资源 → 扩建与解锁。
- **压力修饰器**：生存——生命、饱食和口渴持续变化，灾害/怪物/海域提供风险。
- **空间修饰器**：岛屿侦测与登岛——消耗资源打开新的生产区域和战斗/采集机会。
- **权威长期目标**：可见的岛屿发展与生存天数；它们不能分别维护两套互相冲突的结算。

## 可迁移生产依赖图

```text
基础采集
  ├─ 水/食物 → 维持生存压力，买出操作时间
  ├─ 木/石/纤维 → 基础工具、地板、篝火
  └─ 废料/布 → 容器、工作台与扩建设备

工作台
  ├─ 生产站 → 捕鱼、种植、集水、收集
  ├─ 加工站 → 烧制、烹饪、织布
  └─ 侦测/登岛 → 新岛屿、新矿物、新敌人

高阶工作台/熔炉
  └─ 更高效率、容量、安全或新功能 → 新瓶颈
```

先为每条边写 `输入种类/数量、归属、容量、耗时、失败退款、输出、可见世界变化`。原型只做一条能闭环的纵切，例如：`漂流物 → 木/布 → 工作台 → 捕鱼网 → 食物 → 更远岛屿`；验证后再并行扩展矿物、种植和战斗，不一次实现整棵树。

## UI 与状态合同

| 层 | 最低可见信息 | 失败/恢复 |
|---|---|---|
| 生存 HUD | 生命、饱食、口渴、天数及危险趋势 | 菜单期间是否继续消耗；阈值不足的直接提示 |
| 快捷栏/背包 | 当前物品、数量、容量、选中格 | 满仓、丢弃、死亡掉落、重进恢复 |
| 制作 | 用途、配方、拥有/缺少、可制作状态 | 原子扣料；物资不足不改变库存 |
| 放置 | 占位、上限、朝向、合法表面、确认 | 失败不扣料；拆除返还比例事先可见 |
| 生产站 | 输入、进行中、剩余时间、容量、完成 | 重复领取、满仓、离开/死亡、站点被拆 |
| 扩张 | 侦测成本、目标岛、登岛路径、旧岛返回 | 搜索失败、多人同时侦测、返回与地图边界 |
| 存档 | 权威玩家/岛、快照范围、保存完成、载入来源 | 中断保存、多人冲突、版本升级和干净新局 |

## 持久化边界

代码中存在数十种建筑独立存档键，说明文字把保存权限制为玩家 1，并声明进入自动加载。这个实现可作为风险案例：

- 写存档清单时区分资源、建筑类型、世界位置/朝向、生产队列、岛屿解锁、天数、压力值和一次性奖励；不该保存的临时生成物明确排除。
- 只有一个权威保存者时，其他玩家的建造和消耗如何归属必须提前说明；不能等到退出才告诉玩家没有保存权。
- 保存前锁定交易/放置，快照完成后再反馈成功；加载先清理默认世界，再重建一次，避免重复建筑和重复产出。
- 提供“继续”和“新局”清楚分支；新局必须清空所有经济、建筑、生成物、升级锁和排行榜临时状态。

## 场景实例校准

- 该图用约 43% 的基础方块配合岛屿岩石、树、矿、水和边界件形成可扩建世界；基础件要按“初始裸岛—基础营地—生产聚落—高阶岛屿”分阶段启用或生成。
- 经营图的千件预算不能只做满级成品。每个阶段都要保证碰撞连续、关键站点可读、玩家通道净空，且隐藏/未解锁层不会白白参与物理、投影或逻辑。
- 世界变化优先增加能看见的面积、站点轮廓、容量与运输关系；只改数字、颜色或 UI 文案不算完成升级反馈。

## 不应照搬与未知

- 不复制 100 天、配方数值、Boss/武器树、幸运方块、商城礼包、广告或玩家 1 独占保存。
- 未验证一次完整生产循环、经济节奏、灾害、战斗、多人归属、存档可靠性或第二次进入；所有数值必须以当前目标地图的灰盒测量。
- 若主类型不是生存，不要照搬持续饱食/口渴；压力系统必须服务经营决策，而不是在玩家读菜单时制造无意义失败。

## 身份

- `[元数据事实]` 标签为生存，最低与推荐人数均为 1；`game_time_limit=0`，公开有效时长平均约 1052 秒。地图启用自定义布局、广告和 `use_archive=1`，并以存档整数键建立“生存榜”。

## 视觉证据

- `[视觉观察]` 详情封面用“第 1 天只有小岛/篝火”和“第 100 天出现营地、农田、容器与树木”的前后对照承诺可见成长；实际出生是第 0 天的裸露绿色平台、一个幸运方块和 `5/5` 指示，没有观察到完整岛屿成长。
- `[视觉观察]` 常驻 HUD 分开显示生命 100、饱食度、口渴值、天数、5 格快捷栏，并提供 16 格背包、制作、商城、广告和存档入口。短暂观察中饱食度/口渴值从约 97 继续下降，证明生存压力在玩家查看菜单时仍推进。
- `[视觉观察]` 制作菜单首层可见麻绳、木棍、泥土板、工作台、空杯、拆除锤、木板、篝火；右侧同时展示用途、所需资源和不可制作状态。工作台需要四类资源，文案说明它将解锁更多实用物品。背包初始为空。
- `[视觉观察]` 未制作、采集、登岛、战斗、保存或读取；没有验证完整“输入—加工—交付—升级—新瓶颈”循环，也没有点击商城、广告或存档。

## 代码证据

- `[代码事实]` 归档有 1,051 个批加载渲染单位、18 种模型路径、426 条批合并映射；元数据记录 46,749 次总操作、23,426 个 ECA 触发、102 次编辑地图记录和占用 3,179。可见实例、逻辑与持久化都属于高复杂度口径，但不是同时活动量。
- `[代码事实]` 451 个基础方块模型占约 42.9%；字符串表另有 43 个岛屿岩石、41 棵岛屿树、15 个岛屿铁矿、9 棵枯树、6 个金矿、5 个岛屿、4 艘回家船、4 个怪物生成点和 3 个资源生成点。少模型词汇通过大量基础件与可采集对象形成可扩建世界。
- `[代码事实]` 发布块中的界面与逻辑字面量包含“制作成功”“物资不足”“可建造/不可建造”“当前位置已有组件”“已达上限”“放置成功”“拆除建筑只返还部分物资”“岛屿侦测”“资源生成”“开始烧制/烹饪/捕鱼”“植物浇水成功”等，支持采集、容量、制作、放置、生产和扩张的多环节结构；静态字面量不证明精确事件顺序。
- `[代码事实]` 制作/放置词汇包含岛屿侦测桌、登岛船、捕鱼网、物资收集网、树木种植箱、菜地、蓄水桶、篝火、烤肉架、烹饪锅、织布机、岩石/铁/耀金熔炉，以及工作台、银石工作台、耀金工作台等层级。它们构成“工具/站点解锁新配方与新资源”的依赖图线索。
- `[代码事实]` 存档表列出数十种建筑/地板/工作站的独立存档键；说明文字明确“手动大型存档”“每个建筑有放置上限”“只有玩家 1 能保存”“进入游戏自动加载玩家 1 存档”。这是明确的所有权限制和多人风险，不是通用正确做法。

## 蒸馏

- `[设计推断]` 经营成长应被建模为依赖图，而不是一条长购物清单：基础采集先解决水、食物和安全；工作台解锁加工；更高工作台与熔炉把新矿物转成工具/建筑；侦测与登岛再打开新资源区。每个解锁都必须改变下一轮的瓶颈或空间，而不只是数值变大。
- `[设计推断]` 三条常驻生存压力给经营循环加截止成本：查看菜单、搬运和建造都消耗时间。设计时应确保早期完整产出周期短于压力失控时间，并在菜单中继续显示关键状态或暂停规则，避免玩家因学习界面而无反馈地死亡。
- `[设计推断]` 背包、快捷栏、容量、制作消耗、建筑上限和拆除折损共同形成资源一致性合同。交易必须原子化，放置前检查占位与上限，失败不扣料；拆除返还策略要在确认前可见。
- `[设计推断]` 存档不是一个按钮，而是世界快照范围、权威所有者、保存时机、加载顺序、建筑上限和多人冲突的组合。该图把保存权压给玩家 1 是一种限制性降级；通用方案应优先做到每人/每岛归属清楚，做不到时必须在进入前显著说明。
- `[设计推断]` “第 1 天/第 100 天”前后对照是清楚的视觉目标：升级应让岛屿面积、建筑轮廓、生产设备、植被和容量都可见变化。基础件实例应围绕这些阶段状态组织，不平均撒满初始空地。
- `[设计推断]` 该图的放置校验、建筑上限、拆除折损和世界存档证明“经营/生存中存在建造子系统”不等于“创造沙盒主循环”。玩家是在作者给定的建筑/配方目录中推进生存依赖图；本次没有观察到自由部件目录、预览编辑、任意组合、撤销、个人创作所有权或编辑—测试—返回闭环，因此它只能作为创造沙盒的边界案例，不能替代正向沙盒样本。

- 不复制标题、100 天、幸运方块开局、具体配方、资源名称、Boss、商店/广告礼包、存档公告或封面构图。
- 商城与广告提供的礼包会改变早期瓶颈；本次没有交互，不能把其经济平衡当作无付费路径的证据。设计案例只蒸馏基础循环，不迁移商业入口。
- 未验证首次采集、首个可制作物、单次制作是否原子、建造占位、生产耗时、升级回报、岛屿侦测/登岛、灾害、战斗、死亡、保存/读取、多人资源归属或第二次进入。
- 该案例为经营/生存混合图提供直接 UI、代码和持久化证据，但仍缺完整单局循环与多人实测；不能据此声称经济平衡或存档可靠。
- 不把“可建造/可拆除/可存档”三个词自动解释为自由创作：若核心进度仍由固定配方和预设建筑目录控制，应归入经营或生存的建造子系统，除非另有当前局内创作权、编辑生命周期与测试返回的直接证据。
