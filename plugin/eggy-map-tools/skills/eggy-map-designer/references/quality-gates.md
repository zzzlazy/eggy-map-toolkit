# 地图质量门

这些门用于评审设计成熟度，不是概念生成模板。概念阶段读取“所有地图”和所选主类型相关条目；涉及合作、混合、回合或持久状态时再读对应段。准备坐标、写入预览或部署时，完整读取“世界构成”和“成品装配、密度与性能”，并与专项审计结果对账。

## 所有地图

- 主题承诺在出生区第一视线中可见：至少有一个主地标、一个路线提示和一层环境包裹。
- 玩家在进入首个风险点前能用一句话理解当前目标；核心机制在高失败代价前至少有一次低风险验证。
- 首屏中主任务、下一动作和危险提示先于教程入口、可选能力、社交号召或商业入口被理解；可选系统不得自动遮住出生观察面。
- 每张图都跑一次“取得控制后完全不输入”的基线：不能在契约时长前误判完成、在首个可读提示前遭遇不可避免失败，或因房主选择/可选弹窗而永久停住；刻意放置型体验需明确例外与退出。
- 关键落点能快速判断下一方向；提示来自构图、光色和形状，文字只作补充。
- 每段同时拥有“场景节拍”和“玩法节拍”，相邻段至少在高差、朝向、轮廓或动作之一上变化。
- 关键路径连续，恢复路径闭合；任何可能卡死、掉队或失去必要道具的状态都有明确重置方式。
- 每个可变状态都有唯一作用域/所有者、初始化、合法转换、同源反馈、失败恢复和清理；完成/计分/领取等事件幂等，终局锁后旧机关不能改变结果，连续新局不残留旧代对象或计时器。
- 安全区、危险区、装饰区和不可达背景在碰撞与颜色上有明确分工。
- 多人路线按目标人数保留超车、并行或会合空间，不用单蛋尺寸估算。
- 必经跳跃、门洞、落点、机关窗和载具路线能反查当前版本、能力、碰撞与相机标定；未实测数值标为可调参数，不伪装成精确事实。
- 装饰不能遮挡起跳点、落点、机关运动范围、镜头和终点触发区。
- 最终交付包含假设、未知项和需要人工试玩确认的内容。

## 世界构成与镜头

- 每个拓扑节点和节拍都归入明确世界壳体；每个壳体至少有两个真实相机复核视角、两个比例锚点、两个共享装配族、基线/变化状态与前中远景。`multi_scene` 至少两个壳体，`long_world` 至少三个，不能把全图密度堆在出生首屏。
- 隐藏少量主题 Prefab 后，基础结构仍能通过剪影、比例、装配和材质节奏表达主世界；刻意依赖大型成品资产时说明其承担的层级。
- 社交/展示地图存在可返回的地标网络和至少一个“到达—活动—离开/换景—返回”循环；无强制终点时也能恢复方向。

## 类型、混合与多人合同

- 混合地图只有一个权威终局；次类型通过持续叠层、局部站点、可选支线或有清理边界的阶段换挡强化主循环，不另起一套竞争目标。次类型必须绑定命名节拍，声明强制时间与最长停摆、入口/出口、同时失败裁决和清理所有者；基础件优先形成共享世界和主循环族，不按两种类型平均拆成两套素材包。
- 护送、收集和伙伴任务能让玩家直接看见当前对象、剩余条件与完成反馈；对象丢失、玩家重生或章节重置后不会形成不可恢复的半完成状态。
- 非线性与回合地图的出生、开始、胜负、平局、淘汰/重生、结算和再次开始均有闭环；终局不会留下仍可影响结果的旧状态。
- 可破坏世界为房间/目标建立稳定身份、代次、受损状态和合法伤害来源；同帧命中去重，完成时原子切换碰撞、依赖结构、奖励与出口。碎片有峰值、寿命和清理，玩家脚下的依赖面不会无预告消失；仅摆可打物或销毁特效不构成完整拆解设计。
- 经营图把单件货物/批次、工作站、顾客/员工任务、货币、解锁集合和胜利出口分开建模；每次搬运/加工/上架/出售都是带容量与归属校验的原子事务，目录进度从权威集合复算。
- 有经营存档时明确保存权威、快照范围、加载顺序和新局分支；加载先重建站点/库存/解锁，再恢复交互和出口，不能只恢复总进度数字或保留半完成角色任务。
- 纯音游只有一个谱面时钟；音画提示、判定、输入去重、分数/连击和结算同源，静音、延迟、暂停与第二段序列均可验证和清理。
- Boss 与防守图分别把阶段/伤害/全灭和路径/波次/核心建成权威状态；预告、反制、卡怪、漏怪、多人归属及下一轮不会靠碰巧收敛。
- 潜行图明确检测状态、传感器边界、遮蔽、警戒恢复、目标提交和撤离；恐怖氛围或敌人模型不能代替可读的侦测合同。
- 回合与体育图分别拥有唯一行动权/解析顺序和控球/死球/重启权威；同时输入、掉线、平局、加时与第二局都有闭环。
- 创造沙盒在提交前校验位置与预算，每件作品有所有者和代次；撤销、删除、多人冲突、保存/加载、测试返回和退出清理均可逆或可恢复。
- 阵营推理图把角色分配、私密信息、场上任务/证据、会议、投票、淘汰后权限和多阵营终局置于同一回合权威；公共反馈不泄露身份，掉线、平票、重复报告和第二局不残留旧角色或选票。
- 合作关卡能指出“谁的什么动作改变了谁的什么机会”，并让双方看见因果反馈；否则降级为多人同行图描述。
- 合作角色各自至少拥有一种对共同进度有必要的独占动词；关键交接后双方都能继续行动。允许单人进入时，缺员能力、检查点和复位由明确分支接管，而不是碰巧绕过双人机关。

## 成品装配、密度与性能

- 大量重复物件要有合并、阴影、碰撞或远裁剪策略；不要默认每个装饰都参与物理和投影。
- 千件级地图同时记录全图展开数与峰值可见、碰撞、投影、动态、透明、逻辑、生成和切换成本；性能不足时按预先声明的降级顺序减负，不先删除路线、危险、交互和目标反馈。
- 场景展开密度与状态/触发密度分别预算：低可见实例、高 ECA 的规则图不能用逻辑复杂度冒充环境完成度；高可见实例的场景图也不能用表皮数量冒充玩法闭环。两轴都按主类型说明“为何需要、峰值在哪里、如何降级”。
- 除极小、刻意极简或主要依赖大型成品资产的地图外，约 100–200 个展开实例只视为灰盒；成品必须补齐宏观体量、中层结构、表面细节和氛围层，并说明规划展开总数。成品按空间合同选择密度档而不是按现有数量倒选：微型空间下限 300、主题短图 800、多场景 2000、长世界 5000。低于本档下限仍要作为结构化例外解释 `MASS/MID` 如何由真实空间件或大型资产承担，不能把 301 件当成自动成品，也不能用一句“简约风”放行。不能为追求数量平均撒装饰，也不能因清单过长省略装配展开。
- `micro_space` 只用于真实的一间小房、一个小场域或明确实验；用户要求制作普通成品且空间超过一个可控首屏时，默认至少从 `themed_short` 评估。两个物理分离场景或明显尺度转换从 `multi_scene` 评估，长章节/开放世界从 `long_world` 评估；选择证据必须先于数量预算。
- “首版”只表示第一次可交付版本，不自动等于灰盒；若交付目标是成品，第一次写入预览也要展示四次成品化后的完整展开量。若为降低风险只准备灰盒，必须明确标注成熟度、尚缺层级和后续仍需另行批准的写入，而不能把它称为已完成地图。
- 展开实例必须能说明可见、结构、玩法或系统价值；不可见重叠、无收益微分面和纯凑数散布不计入成品化。装配公式、区域预算、分层预算与最终实例清单必须对账。
- 参数化配方必须声明局部基向量、入口/出口接口、净空、受控变体和共享件所有者；部署前解析为每件唯一名称与世界变换，不能把“重复 N 次”当成已完成清单，也不能用未验证镜像或欧拉角约定猜坐标。
- 总设计账承诺的展开总数与分层必须和实际参数化清单完全一致；成品装配计划声明 `expected_total`，重复四次以上的装配族检查已声明且实际使用的变体。任何 `predeploy` 方案都必须让密度账的总数、区域、分层、灰盒数、资产词汇数及低数量例外与其他账本一致，不能通过把总数压到阈值下绕过门禁。
- 成品装配计划的 `quality_contract` 必须覆盖每个实际可见区域；其区域与 `theme.world_shells[].assembly_zones` 双向一致，主题及各壳体承诺的装配族以同名可见实例落在对应区域。展开器按每件尺寸与世界基向量计算真实轴对齐包围盒：任何空间件越过全图/分区边界、同构成类别出现完全相同的位置/朝向/尺寸、壳体/区域或装配族挂名、全图或区域低于承诺的可见实例/装配族/空间跨度/设计职责数量，或重复四次以上却只有单一变体且没有结构/公平理由，均不得进入部署。职责数量只接受空间可见职责，不能用 `COLLISION/LOGIC` 充当世界完成度。
- 每个展开件标明 `BASIC_PRIMITIVE/THEME_ASSET/GAMEPLAY_DEVICE/COLLISION_PROXY/FX_LIGHT_AUDIO/LOGIC_ONLY` 构成来源；成品声明基础件主导、混合或资产主导策略与最低可见基础件占比。资产主导可以成立，但要说明大型资产承担的层级，不能把机关和逻辑件计作环境完成度。
- 每个展开件还至少标明一个设计职责：`SILHOUETTE/ENCLOSURE/STRUCTURE/CONTACT/NAVIGATION/DANGER/INTERACTION/GOAL/STATE_FEEDBACK/SCALE_REFERENCE/SURFACE_DETAIL/ATMOSPHERE/COLLISION/LOGIC`。碰撞代理与纯逻辑件必须分别包含 `COLLISION/LOGIC`；可见基础件、主题资产和视听件不能只写这两个不可见职责。成品全图至少显式承诺轮廓、结构和导航，各关键区域再声明自身必需职责。
- 可见世界构成占全图展开实例的最低份额随密度档提高：`micro_space=20%`、`themed_short=35%`、`multi_scene=40%`、`long_world=45%`；只统计 `MASS/MID/PROP/ROUTE` 中的基础件与主题资产，机关、碰撞、特效和逻辑不能把百件壳体虚增成千件成品。
- 完整方案的设计总账必须覆盖体验、拓扑、节拍、主题、类型专项合同、装配预算、证据边界和类型驱动的试玩矩阵；`predeploy` 不得仍含 planned 验证或阻塞未知项，专项审计状态必须与本次实际结果一致。
