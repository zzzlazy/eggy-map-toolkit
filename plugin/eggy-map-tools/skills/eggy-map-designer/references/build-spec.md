# 可实施搭建规格

完整方案先按 [全类型设计计划审计](design-plan-audit.md) 建立跨层总账；本文件负责把已闭合的玩法、主题和状态进一步落到组件、装配与坐标。总账通过不代表实施规格已完成，实施清单也不能反过来替代类型合同。

## 先固定坐标语义

读取现有地图后再确定主前进轴、地板边界、出生朝向、垂直轴与安全高度。不要套用上一张地图的坐标。对每个章节给出包围盒、连接口、镜头观察方向和不可侵入区域。

精确尺寸前读取 [玩家尺度、相机与空间标定](spatial-calibration.md)，记录当前版本、角色/能力、设备、镜头和目标人数；把 `B/H/Jc/Jm/Jx/Vc/Vm/Lerr/S/E/C/Tr` 或载具等价量写入标定表。没有实测的数据标为 `TBD-PLAYTEST`，用参数化表达保留调优空间。

## 主题卡与关键镜头表

坐标前按 [视觉主题与世界构成蓝图](visual-theme-playbooks.md) 固定：世界句、记忆剪影、比例词、3–6 类主基础件、3–8 个装配族、材质节奏、环境/路线/危险/交互/目标色、至少一种世界状态变化和禁用清单。

再为出生首屏、每个章节入口/转折、机制教学点、主要活动点和终点建立镜头条目：

- 相机观察位置、朝向和主要视锥；
- 前景接触面、中景可达锚点和远景地标；
- 主轮廓、路线开口、危险边界和目标在灰度下的明度关系；
- 本镜头需要出现的 `MASS/MID/ROUTE/PROP/FX` 装配族与预计展开量；
- 必须保持净空的落点、机关运动、多人数站位、合影和 UI 可读区域；
- 世界状态变化前后的保留项、变化项与玩家可见反馈。

关键镜头只写“放一些工厂/森林装饰”不合格；必须能追溯到基础件、装配族和实际展开量。

## 分层命名

为受管组件使用稳定前缀，并在逻辑名中包含区域、层和职责，例如：

`<MAP>_<ZONE>_<LAYER>_<ROLE>_<INDEX>`

常用层：

- `COL`：承重与碰撞骨架；
- `MASS`：主场景体量；
- `MID`：梁柱、边框、支撑、分缝和结构收口；
- `ROUTE`：路线提示；
- `MECH`：机关；
- `PROP`：主题装饰；
- `FX`：灯光与特效；
- `LOGIC`：触发与系统；
- `SAFE`：保护边界与恢复区。

## 组件表字段

每个准备写入的组件至少包含：

- 稳定逻辑名与职责；
- 当前目录返回的 `component_ref`、EID、名称和证据等级；
- 中心坐标、旋转、目标尺寸/缩放、颜色；
- 父子或编组关系；
- 碰撞、物理、阴影与可见性意图；
- 属性白名单内的配置；
- 与相邻落点、机关扫掠范围和地图边界的净距；
- 失败后的回收路径与人工验收点；
- 主题角色：骨架、表皮、接缝、路线、状态反馈或焦点，并注明它服务的关键镜头。
- 所依赖的空间标定量与适用上下文；必经动作不能只写一个没有来源的距离。

参数化计划先按 [组件角色绑定与可写证据](component-binding-audit.md) 生成完整 `component_role` 模板，再批量查询当前目录并填写候选。装配种子可同时使用 `--binding-output`；普通装配计划运行 `scripts/audit_component_binding.py <assembly-plan.json> --template --output <binding.json>`。`predeploy` 要求每个实际角色都有 `verified_writable` 证据、具体游戏版本与 `device_status=writable`；未查询角色不得填写引用或名称。一个基础组件可以服务多个抽象角色，但每个角色仍分别记录其枢轴/缩放、碰撞、投影、材质槽和替换约束。

组件有据可写仍不代表千件骨架已经拥有题材。参数化计划同时按 [题材适配账与视觉证据](theme-adaptation-audit.md) 为每个实际装配族记录形状/结构/材质/变体合同，为每个区域记录前中远景、比例锚点、路线或活动可读性和密度理由。运行 `scripts/audit_theme_adaptation.py <design-plan.json> <assembly-plan.json> --template --output <theme-adaptation.json>` 起稿；`predeploy` 要求族和区域全部经过命名游玩视角复核，并完成黑白剪影、去 Prefab、三距离、灰度、重复、状态、净空与成本八项测试。只换色、改族名或在通用壳体上零散挂主题件不算完成适配。

机关或触发链还要记录：输入者、输入条件、被改变的对象、可见/可听反馈、持续时间、复位条件、断线或掉队时的兜底。不能只写“按钮控制门”而不写因果链和恢复。

## 装配配方与展开表

高完成度场景先按 [基础件装配与成品密度](assembly-and-density.md) 定义装配族，再生成实例。每个装配族记录：

- 局部原点、局部包围盒、对接接口和允许的整体旋转/镜像；
- 局部件清单、相对坐标/旋转/缩放、材质色阶与层职责；
- A/B/C 变体保留项和可变项；
- 单体展开件数、计划重复数、总展开件数；
- 碰撞代理、可见表皮、阴影、物理与合并策略。

沿直线、折线、圆弧、网格、中心辐射或垂直结构重复时，按 [参数化装配与千件级坐标展开](parametric-layout.md) 另列布局生成器、局部 `u/v/f` 基向量、入口/出口接口、接口误差、净空盒、确定变体序列和共享件所有者。公式只用于生成；最终清单不能保留“重复 N 次”或未解析参数。

数百件以上的参数化计划先运行 `scripts/expand_assembly_plan.py <plan.json> --output <temporary-expanded.json>`。抽查直线首尾、折线每次换向、圆弧尾缝、辐射朝心/朝外、垂直首末层和 A/B/C 变体，再把展开摘要写入密度账本；脚本输出的世界基向量仍需按当前版本验证后的旋转/枢轴语义转换，不能直接冒充可写游戏旋转。只有主类型而尚无装配计划时，可用 `scripts/generate_type_assembly_seed.py --type <主类型>` 获得基础件设计种子，并用 `--design-output/--density-output/--binding-output/--theme-output/--performance-output` 同时生成算术对齐的概念总账、灰盒阶段密度账、未解析组件角色表、未解析题材适配表和未测逐视区性能账。前三账通过只证明类型起点、世界壳体路由与数量一致；后三表只证明组件角色、题材适配对象和性能视区没有漏项。它们不含成品质量合同、真实地图边界、已验证 EID、游戏轴向、目标设备结果或试玩证据，不能直接进入写入预览。

全图再按区域汇总 `COL/MASS/MID/ROUTE/MECH/PROP/FX/LOGIC`。装配配方可以压缩设计文档，但写入预览必须展示展开后的真实实例数；实际部署前必须生成明确实例清单，不能把一行“重复 20 次”误报成一个组件。

每个装配族和独立件再标记 `VIS_STATIC/COL_PROXY/FOCAL_SHADOW/DYNAMIC_MECH/TRANSPARENT/LIGHT_FX/LOGIC_TIMER/SPAWNED` 中的主要成本角色；详细视区预算与降级顺序见 [性能与降级预算](performance-and-budget.md)。参数化计划运行 `scripts/audit_performance_plan.py <design-plan.json> <assembly-plan.json> --template --output <performance-plan.json>`，从真实区域反算候选上限，再填写冷进入、稳定镜头和最大人数最坏交互；全图件数或发布缓存统计不能代替这些结果。

成本角色之外，再标明构成来源：`BASIC_PRIMITIVE` 是可变形方块、圆柱、棱柱、薄片、环件等基础几何，`THEME_ASSET` 是成品场景/道具模型，`GAMEPLAY_DEVICE` 是机关或玩法设备，`COLLISION_PROXY` 是碰撞代理，`FX_LIGHT_AUDIO` 是特效、灯或声音，`LOGIC_ONLY` 是纯触发/状态件。两套标签不能互相替代：同一个基础方块可以是低成本静态表皮，也可以是碰撞代理。成品装配计划还要声明 `primitive_led/hybrid/asset_led` 构成策略、最低可见基础件占比和理由；占比只在 `MASS/MID/PROP/ROUTE` 的基础件与主题资产之间计算，不让机关、碰撞或逻辑件虚增场景完成度。`quality_contract.minimum_world_visible_share` 还要达到密度档下限：`micro_space=0.20`、`themed_short=0.35`、`multi_scene=0.40`、`long_world=0.45`。这是硬门禁；大型主题资产仍计入可见世界构成，逻辑件、机关、碰撞代理和特效不能拿来凑比例。

展开后必须通过数量一致性审计：

- 每个实例拥有唯一、稳定的逻辑名，并能反查 `装配族 / 放置编号 / 变体 / 局部件`；
- 每个展开件拥有明确世界位置、世界朝向/基向量和目标尺寸；转角、尾端、镜像、共享接口与组件枢轴已显式处理；
- `装配展开 + 独立件` 总数等于区域汇总，也等于分层汇总和待写入清单总数；
- 变体删件、共享碰撞代理、合并输出和裁掉背面造成的差额逐项记录；
- 灰盒与成品的差额能落到 `MASS/MID/PROP/FX` 等明确层，不以一句“后续美化”代替；
- 不可见重叠件、无收益微分面和纯凑数散布标为错误，不进入部署清单。

任何准备部署的成品都应把数量账本保存为临时 JSON，并运行 `scripts/audit_density_plan.py <plan.json>`；数百件以上通常由参数化展开生成，低数量成品则用同一账本证明它不是阈值规避。最小结构为：

```json
{
  "schema_version": 1,
  "stage": "final",
  "density_profile": "themed_short",
  "density_profile_evidence": "一个连续主题场域，出生、两个转折和终点都需要完整环境壳体",
  "graybox_total": 120,
  "asset_vocabulary_count": 24,
  "assemblies": [
    {
      "name": "RUN_PLATFORM",
      "pieces_per_instance": 20,
      "placements": 26,
      "adjustment": 0,
      "zones": {"RUN": 520},
      "layers": {"COL": 26, "MASS": 104, "MID": 260, "ROUTE": 52, "PROP": 78}
    },
    {
      "name": "WORLD_BAY",
      "pieces_per_instance": 30,
      "placements": 10,
      "adjustment": 0,
      "zones": {"WORLD": 300},
      "layers": {"MASS": 120, "MID": 120, "PROP": 60}
    }
  ],
  "independent": [
    {"name": "FINISH_FX", "count": 30, "zone": "FINISH", "layer": "FX"}
  ],
  "declared": {
    "expanded_total": 850,
    "zones": {"RUN": 520, "WORLD": 300, "FINISH": 30},
    "layers": {"COL": 26, "MASS": 224, "MID": 380, "ROUTE": 52, "PROP": 138, "FX": 30}
  }
}
```

`adjustment` 用于记录变体删件、共享代理或额外收口造成的净差额；每个装配族的区域和分层之和仍必须等于调整后的展开量。`density_profile` 使用 `micro_space/themed_short/multi_scene/long_world`，对应 300/800/2000/5000 件审计下限；选择来自真实空间合同，不从现有数量倒推。低于所选档位下限的 `stage=final` 密度账还要携带与总设计账完全相同的 `low_count_exception`，解释例外模式、空间尺度、`MASS/MID` 承担者、两个以上视觉复核视角和取舍。脚本只验证算术、名称和基本成熟度信号，不证明视觉、碰撞或玩法正确；临时账本不打包进技能，也不代替写入技能的部署预览与批准。

三个账本分别通过后还不够：总设计账可能承诺 1600 件，参数化清单却只展开 100 件，而手写密度账又描述另一份布局。部署前运行跨账本门禁：

```bash
python3 scripts/audit_build_bundle.py design-plan.json assembly-plan.json \
  --density-plan density-plan.json --json
```

它会重新审计总设计账与参数化输入，并要求总展开数和所有层完全相等；逐件反算区域、层、成本角色、构成来源和设计职责；检查最终装配计划已声明 `expected_total`、构成策略与最低可见基础件占比，没有未使用的装配族，且主题承诺的装配族都以同名实例出现。成品还必须声明 `quality_contract`：全图构建边界、最低可见世界占比、必需完成层与设计职责、全图最低职责实例数、每个可见区域的边界/最低实例/装配族/空间跨度/必需职责及最低职责实例数，以及确需完全统一重复的装配族例外理由。`minimum_design_role_counts` 的键必须与同级 `required_design_roles` 完全一致且值至少为 1；质量合同不接受 `COLLISION/LOGIC` 作为可见世界职责。门禁再把 `theme.world_shells[].assembly_zones` 与 `quality_contract.zone_targets` 双向核对，并确认每个壳体承诺的装配族在其区域内确有可见世界实例；拒绝文案中有场景却没有展开区、挂名装配族或有可见展开区却不属于任何壳体。它按世界基向量和尺寸计算真实包围盒，拒绝越界、同类别完全重合、漏区、缺层/职责、职责数量缩水、低于区域承诺或无解释的单变体批量复制。密度账还会对齐密度档、选择证据、总数、区域、分层、灰盒数、资产词汇数和低数量例外；所有 `predeploy` 构建缺少密度账都会被拒绝。脚本证明三个工件描述同一份构建且没有明显的空间刷量，但仍不证明画面、碰撞、组件引用或游戏内性能正确。

## 空间与路线表

坐标表之前先给每个节拍一个空间条目：

- 入口和出口的中心、朝向、净宽与可见关系；
- 关键路径、可选路线和恢复路线；
- 起跳面、落点、等待区和机关扫掠区的包围盒；
- 玩家相机观察方向与必须保持无遮挡的视锥；
- 近景碰撞层、主题体量层和不可达背景层的职责；
- 本段的动作压力、认知压力、视觉强度和目标耗时。

多人或合作地图再标记每名玩家的占位区、交叉点、等待成本和重新会合位置。不要等组件落坐标后才发现路线拓扑无法恢复。

## 从骨架到细节

复杂项目优先按以下成熟度阶段准备：

1. 玩法骨架与安全边界；
2. 机关与触发；
3. 空间体量、远景轮廓与路线提示；
4. 中层梁柱、边框、支撑、平台侧脸与结构收口；
5. 主题表皮、近景细节、灯光、特效和优化。

复杂机制可在第 1 阶段使用代理方块、颜色块和临时文字完成灰盒，不必等待主题资产。灰盒验收失败时优先改拓扑、尺寸或时序，避免用装饰掩盖结构问题。

这些阶段可以先完整设计、最后一次部署；阶段划分不等于自动获得多次写入授权。每次外部写入都要重新说明目标、展开实例数量、保留项、清理策略和副作用，并取得对应批准。不能因为只获批一次写入，就省略后三个成品层。

## 规则与状态表

按 [触发、状态机与重置模式](logic-and-reset-patterns.md) 先确定状态作用域与唯一所有者，再列状态表、转换表、能力落地表和整局验证矩阵。抽象事件、条件和动作只有映射到当前目录可证明的组件/机制后才能进入实施清单。

非线性、回合、阵营、积分或生存地图在组件表之前列出：

- 准备、开始、进行、阶段变化、胜负/平局、结算和重置状态；
- 每个状态的进入条件、退出条件、玩家可做的事和 UI/声光反馈；
- 出生、重生、淘汰、观战、掉线或中途加入的处理；
- 队伍、分数、计时、资源和一次性触发在下一局如何清零；
- 同一触发重复执行、同时执行或越序执行时是否保持幂等；
- 无人达成目标、所有人同时失败或时间结束时的兜底；
- 每个生成物、计时器、运动机关和一次性触发的代次/取消条件，以及死亡、换章、终局和新局时的清理动作；
- 同帧冲突的优先级，例如终点与危险、得分线与计时结束、两人同时领取或淘汰。

复杂状态图把设计账本写成临时 JSON，并运行 `scripts/audit_state_plan.py <plan.json>`；其中 `primary_type/secondary_type` 必须与总设计账一致，脚本再把类型、混合交接和实际功能合并成必测场景矩阵，详见 [触发、状态机与重置模式](logic-and-reset-patterns.md)。脚本通过只证明设计图自洽，不证明当前组件能够实现。

静态组件齐全不代表整局可结束。状态表未闭环或状态账本未通过时，不进入精确坐标和批量部署。

## 写入预览

部署前向用户展示：

- 组件总数及各层数量；
- 灰盒数量、成品规划展开总数、资产词汇数，以及每个装配族的单体件数 × 重复数；
- 新增、更新、删除和去重范围；
- `managed_prefix` 与 `cleanup_policy`；
- 明确保留的出生点、终点、触发、地板、相机和用户自建内容；
- 仍未验证的机关方向、速度、周期、特效尺度与账号 UI 可见性；
- 仍未验证的移动、相机、多人和载具标定量，以及它们影响的组件范围；
- 逻辑状态/转换总数、同时运行对象、清理范围，以及目录尚未证明或只能依赖默认行为的触发链；
- 最坏视区/状态下的可见、碰撞、投影、动态、透明、逻辑与生成峰值，目标设备结果和不达标时的降级顺序；
- 预期缓存重建和回滚方式；
- 主题卡摘要，以及关键镜头的近/中/远景覆盖、路线净空和状态变化覆盖情况。

若预览只给“装配体 20 组”而不显示其展开后的真实组件数，或公式、区域、分层、清单四种计数不能对齐，不得把它称为成品部署预览。

禁止把目录未开放的字段写入 `properties`。成品组件的模型尺寸与目标世界尺寸可能不同，必须通过目录 Profile 的缩放换算，不能直接把尺寸当缩放。

## 验收

离线检查覆盖：严格解码、层级、引用闭包、缓存子集、静态碰撞与声明计数。人工编辑模式检查覆盖：

- 出生第一屏、终点和下一落点是否清楚；
- 关键镜头是否同时拥有接触面厚度、环境包裹、中层结构、远景地标与近景尺度细节，留白是否有明确构图目的；
- 隐藏少量主题 Prefab 后，基础件形成的剪影、比例、接口与材质节奏是否仍能表达主世界；
- 是否存在穿模、悬空、遮挡、误碰撞和地图外物件；
- 抽查装配族 A/B/C 实例，确认接口连续、变体有节奏且没有机械复制、重叠或缺失局部件；
- 机关实际方向、扫掠范围、多人拥堵和复位位置；
- 重复触发、同帧、越序、死亡/掉线、终局和连续新局后，状态、对象、计时器与反馈是否一致；
- 必经落点、门洞、转角与机关窗口是否符合当前标定，视觉表皮与实际碰撞是否在边缘一致；
- 雾、灯光和高饱和提示是否影响落点辨识；
- 目标设备帧率和远景加载是否稳定。
- 最坏人数/状态、快速移动、传送/换景、重生和连续多回合后是否出现渐进掉帧、输入迟滞或迟加载。

结构校验通过不代表视觉正确。部署后先进入编辑模式等待缓存重建；正常才保存退出，异常则不保存退出并按新的批准回滚。
